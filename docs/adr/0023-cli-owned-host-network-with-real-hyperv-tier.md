# Host network setup is CLI-owned, verified by a real-Hyper-V test tier

The Internal switch, its host IP assignment, and the inbound firewall rules that admit VM traffic — previously a manual `setup-machine.md` step plus the per-environment templated `host-allow-vm-inbound.ps1` — become two CLI-owned commands, `susentorno create-host-network` and `susentorno delete-host-network`. Both are host-level (not tied to any environment directory, unlike `setup-guest-unix`) and gate on an elevated terminal via the same `isElevated()` check `setup-guest-unix` already uses. `create-host-network` refuses to *recreate* an existing switch, but is safe to rerun against one: it refreshes the firewall rules only (clearing and recreating them fresh, using the switch's already-assigned host IP), never touching the switch or its IP. This restores the "safe to rerun" property `host-allow-vm-inbound.ps1` already has today — needed because the Default Switch's IP can drift across host reboots, which would otherwise silently break only the SMB rule's NAT-side half. `delete-host-network` remains the way to fully recreate the network from a clean state (a different subnet, for example). `delete-host-network` is deliberately not scoped to only what a matching `create-host-network` made: it sweeps every firewall rule on the Internal-switch adapter's interface regardless of name or origin, plus every rule named `<prefix> share (VM inbound)` on any adapter (catching the SMB rule's Default-Switch/NAT-adapter half), then removes the switch by name if found — each action independent and safe to rerun, so it doubles as a "return this adapter to a pristine state" tool for a corrupted host, not just an undo for what this project itself created.

A fixed default name (`susentorno-internal`, matching the existing `DEFAULT_INTERNAL_SWITCH_ADAPTER` constant) is used unless `--isolation-name <name>` is given, which renames the switch to `susentorno-<name>-internal` and prefixes every firewall rule's `DisplayName` with `susentorno-<name>` instead of `susentorno`. This exists so automated tests can create and delete a fully separate, sandboxed network (`susentorno-test-internal`) without ever touching a developer's real `susentorno-internal` switch — the same physical machine can safely host both at once.

This closes the "Windows-specific binding/firewall behavior is covered only by manual checkpoints" gap [[vm-tests-via-qemu-in-wsl2]] names in its residual fidelity gaps — but only for the switch/firewall-*creation* surface. `run-hosting`'s own DNS/DHCP socket-level Windows binding behavior is untouched by this decision and remains manual-only. This is a deliberate, narrow exception to that ADR's stance that "Hyper-V remains the production guest platform and is not the test runtime": host-level switch/firewall operations, unlike guest-boot behavior, can be fully sandboxed via `--isolation-name`, so there's no fidelity trade-off in testing them against the real thing. Guest OS behavior has no equivalent safe-sandboxing mechanism, which is exactly why that ADR's QEMU substitution still stands for the `guest` tier.

## Status

accepted (2026-08-10)

## Considered Options

- **Leave Hyper-V/firewall verification as a manual checklist**, the same treatment `setup-guest-unix-isolation-checklist.md` gives guest isolation. Rejected: unlike guest isolation (state entangled with a specific VM's boot/OS behavior, hard to sandbox), switch/firewall creation is cleanly sandboxable via `--isolation-name`, so there's no fidelity cost to testing it for real — a manual-only checklist would be trading away free, safe coverage for no real benefit.
- **Fold host-network coverage into the existing `cli` tier.** Rejected: it would force every `cli`-tier test — including ones unrelated to Hyper-V — to require an elevated shell, and `cli` runs unconditionally in the default `pnpm test` pipeline. A dedicated `host-network` tier keeps the admin/Hyper-V prerequisite scoped to exactly the tests that need it, following the same per-tier-prerequisite precedent `proxy-stack` (Docker) and `guest` (WSL2/KVM) already set.
- **Keep host-network tests out of the default `pnpm test` pipeline entirely** (opt-in only). Rejected: it would leave `create-host-network`/`delete-host-network` regressions uncaught by routine test runs, undermining the point of writing real tests instead of a checklist. Wiring `host-network` into the default pipeline (alongside `guest`) costs contributors an elevated shell for a full green run — accepted, matching the WSL2/KVM cost `guest` already imposes.

## Consequences

- `templates/proxy/host-allow-vm-inbound.ps1` is deleted outright; `susentorno init` no longer templates it into a fresh environment's `.susentorno/proxy/`.
- `setup-machine.md`'s two manual steps (create switch + assign IP, then run the firewall script) collapse into one: run `susentorno create-host-network` as Administrator.
- `setup-environment.md` loses its per-environment "open the host firewall if this is your first environment" callout — firewall setup has no per-environment trigger anymore; it's purely a pre-environment, host-level step.
- `verify-proxy.ps1`'s diagnostic hints and comments, which currently name `host-allow-vm-inbound.ps1` directly, are updated to point at `susentorno create-host-network` instead; its rule-matching logic is unaffected since the same fixed `DisplayName`s are preserved.
- A new `host-network` test tier (`pnpm test:host-network`, `tests/host-network/`, `vitest.host-network.config.ts`) joins the default `pnpm test` pipeline. Its startup gate fails fast (not skip-silently) when the shell isn't elevated, matching the existing "a missing live-tier prerequisite is an environmental failure, not a product failure" philosophy `proxy-stack`/`guest` already establish.
- [[vm-tests-via-qemu-in-wsl2]]'s "Residual fidelity gaps" bullet is updated to reflect that firewall/switch-creation now has real automated coverage, while DNS/DHCP socket binding remains manual-only — see that ADR's update.
- Depends on [[hyper-v-only-target]] for the Hyper-V cmdlets involved, and implements the firewall-boundary assertion [[transparent-interception-and-network-isolation-boundary]] already describes at a design level — this ADR is about *who owns creating* those rules, not a change to what they enforce.
- The isolation name is no longer a `create-host-network`/`delete-host-network`-only concept. `run-hosting --isolation-name <name>` binds that network's adapter instead of the default one, and `setup-guest-unix --isolation-name <name>` attaches the guest to that network's switch — replacing `run-hosting --forward-listen <ip>` and `setup-guest-unix --adapter-alias <alias>`, both removed. All four commands take their switch name and adapter alias from the same `resolveHostNetworkNames`, so the two can never disagree, and a hand-made Internal switch not named `susentorno-<name>-internal` is no longer supported.
