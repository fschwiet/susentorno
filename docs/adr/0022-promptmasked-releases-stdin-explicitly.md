# `promptMasked` releases stdin explicitly instead of adopting a prompt library

`setup-guest-unix` prompts for the SMB share password (`promptMasked`, in `src/cliPrompt.ts`) and then immediately spawns `ssh` with `stdio: 'inherit'` (`createSshRemoteExec`) for the guest's own login prompt. On Windows, `promptMasked`'s raw-mode/`keypress`-event reading left Node still contending for the shared console input buffer after it returned, so the subsequent `ssh` password prompt silently never received the typed password — keystrokes registered (visible as brief CPU activity on the `ssh` process) but never reached it, with no error, no re-prompt, and no way to tell the run had stalled versus a slow remote step. Root cause: `node:readline`'s `emitKeypressEvents(stream)` attaches an internal `data` listener with no public removal API, which keeps the stream in flowing mode — and therefore still reading from the console — even after `promptMasked`'s own `keypress` listener is removed and raw mode is turned back off.

The fix is `input.pause()` in `promptMasked`'s cleanup path, called unconditionally (not just on TTY input) right before resolving or rejecting. `pause()` forces the stream out of flowing mode regardless of what other listeners remain attached to it, which stops Node's own reads from the console so a subsequently-spawned child inheriting stdio can read it instead.

We considered replacing `promptMasked` with a maintained third-party library instead of patching this ourselves, on the theory that a widely-used library would have already solved this class of problem. It doesn't fit: masked-input libraries are built and tested exclusively for real interactive terminals. We spiked `@clack/prompts@1.7.0` (the strongest current option — actively maintained, ~500K weekly downloads) by driving it exactly the way this repo's CLI tests already drive prompts, piping an answer string into a spawned child's stdin (`execa(..., { input: '...\n' })`); it never resolves — the piped characters are consumed as literal keystrokes but the terminating `\n` is never recognized as submit, and the process only ends when Node force-exits on an unsettled top-level await. `readline-sync`'s masked `question()`, spiked the same way, hangs even harder (no output at all). Every other library the search turned up (`prompt-sync`, `password-prompt`, `minimal-password-prompt`, `prompt-password`) hasn't been published in 2–4 years. Clack's own repository has no test suite covering non-interactive driving of its prompts either — this is a real, unaddressed gap across the ecosystem, not a configuration option we missed.

## Considered Options

- **Adopt `@clack/prompts`.** Rejected: cannot be driven by piped stdin (see above), which would silently break `tests/unit/cliPrompt.test.ts`'s existing `promptMasked` unit tests (they inject non-TTY `PassThrough` streams the same way the spike's pipe was non-TTY). Adopting it would trade an in-house fix we can partially regression-test (that `pause()` gets called) for a library-backed one we could not test at all, while adding a dependency and a visual-style change to every prompt in the CLI for no net testability gain.
- **Adopt a smaller/older masked-input library** (`readline-sync`, `prompt-sync`, etc). Rejected: spiked and confirmed no better on piped input (see `readline-sync` above), and several are stale enough (2–4 years since last publish) to undercut the "well-tested" rationale for reaching for a library in the first place.

## Consequences

- `promptMasked`'s existing exported signature and its injectable `PromptStreams` (`input`/`output`) are unchanged; only the cleanup path gained one call. `tests/unit/cliPrompt.test.ts`'s three existing `promptMasked` tests continue to run exactly as before, plus two new ones asserting `input.pause()` is called after a normal submit and after a cancellation (Ctrl+C) respectively.
- The actual real-world fix (that a subsequently-spawned `ssh` can now read the console) cannot be verified by any test tier in this repo, the same limitation that already applies to `createSshRemoteExec` itself (see the original guest-setup plan's Task 5 note). It can only be verified by manually re-running `setup-guest-unix` against a real guest, which is a required step before this fix is considered done.
