Cold Envoy DNS cache / flaky real-network passthrough in VM tests
===================================================================

Observed while adding tests/vm/vm.test.ts's "S2b: run-proxy inline logging"
suite (docs/superpowers/plans/2026-07-10-run-proxy-merge-config-and-logging.md,
Task 9).

Symptom
-------

`curl` to a real internet passthrough host (pypi.org, SNI passthrough — the
only kind of traffic this proxy setup can't mock) sometimes fails from the
guest VM with either:

  - curl exit 35 (CURLE_SSL_CONNECT_ERROR) — consistently and reproducibly
    (3/3 runs) when the curl fires immediately after a live run-proxy
    restart (waitForAdminReady() returning does not guarantee the freshly
    recreated Envoy container's passthrough path is warm), or
  - curl exit 28 (CURLE_OPERATION_TIMEDOUT) — intermittently, even on an
    unmodified, pre-existing test unrelated to this plan's changes
    (S2 "passthrough :443 host works end-to-end"), suggesting some baseline
    flakiness reaching the real pypi.org from this nested WSL2/QEMU VM
    setup that is independent of run-proxy's restart logic.

Root cause (working theory, not confirmed against Envoy source/docs)
----------------------------------------------------------------------

The passthrough :443 listener uses Envoy's SNI dynamic-forward-proxy filter
(src/envoyConfig.ts, `sni_dynamic_forward_proxy` + `dynamic_forward_proxy_cluster`),
which resolves the upstream host's DNS lazily per-cluster, with an in-memory
DNS cache scoped to the container's lifetime. On a freshly recreated
container (`docker compose up --force-recreate`), that cache is empty. The
admin `/ready` endpoint (used by waitForAdminReady) reports readiness once
Envoy's own initialization completes, but that doesn't appear to guarantee
the dynamic-forward-proxy DNS cache is warm for a specific host — so the
very first passthrough connection to a not-yet-cached host can fail at the
TLS layer (client sees a dropped/reset connection mid-handshake) before the
cache populates. This reproduced deterministically (3/3 runs) for pypi.org
curl'd immediately after a restart, but never for pypi.org curl'd later in
the same test run once it had already been resolved once.

Separately, the exit-28 timeout on the pre-existing S2 test (which curls
pypi.org well after the guest has been up, not immediately post-restart)
looks like plain real-network unreliability in this environment (nested
WSL2 + QEMU + Docker Desktop + real internet), not related to the cache
issue above.

UPDATE 2026-07-11: working theory tested and REFUTED as the cause
-----------------------------------------------------------------

The theory above conflates two variables that the original observation
never separated: container age (fresh-recreate vs. long-warm) and host
freshness (un-resolved vs. already-cached). Every post-restart failure was
also a first-ever resolution of pypi.org, and every later success was also
an already-cached pypi.org — so "cold cache" and "just restarted" were
indistinguishable in the data.

The tests/vm/vm.test.ts "S2c" block probes the cell that disentangles them:
three hosts (files.pythonhosted.org, github.com, www.google.com) allow-listed
from startup but contacted by nothing until a single, un-retried curl fired
while the Envoy container had been up since beforeAll with no recent restart.
Envoy resolves passthrough DNS lazily, so each host's DNS cache entry was
genuinely empty at first contact.

Result (2/2 runs, all three hosts): first contact SUCCEEDED cleanly —
http=200, curl exit=0, and the proxy logged ALLOW PASS for each. No exit 35,
no exit 28.

Conclusion: a cold DNS cache is NOT sufficient to reproduce the exit-35
failure. On a warm container, a never-before-resolved host pauses-and-resolves
exactly as Envoy's dynamic-forward-proxy design intends (pending-request
queue on cache miss), then connects. The failure is specific to the
freshly-recreated-container window, i.e. a restart/warmup race (Docker Desktop
/ WSL2 port-forward re-establishment during --force-recreate, or an Envoy
worker/listener not yet truly serving the passthrough path despite /ready
returning) — not the DNS cache. This means preresolve_clusters (listed below)
would NOT fix it; a passthrough-path-specific readiness gate after a restart
would.

UPDATE 2026-07-11 (b): boundary-isolation probes REFUTE both standing candidates
--------------------------------------------------------------------------------

The two candidates the S2c update left standing were (a) Envoy worker/listener
not serving the passthrough path despite /ready, and (b) a Docker Desktop / WSL2
port-forward re-establishment blip during --force-recreate. Both were probed
directly by replaying the production restart (docker compose up -d
--force-recreate) and firing un-retried passthrough TLS probes to pypi.org at
each component boundary, WITHOUT the QEMU guest. Container replacement was
verified by container-id change each iteration (not just /ready), because the
OLD container keeps answering /ready during a recreate — gating on /ready alone
lets a probe hit the warm old container and hide the post-recreate window.

  1. Host loopback -> Docker(Windows republish) :18443 -> Envoy passthrough,
     container-id-gated, probe fired the instant the NEW container's /ready hit
     200: 24 probes, 0 exit-35. (The only failures were exit-28 body-transfer
     timeouts on the multi-MB https://pypi.org/simple/ page — TLS handshake
     already complete, http=200 received — i.e. the doc's separate real-network
     flakiness, reproduced and explained as a slow large-body download, not a
     TLS drop.)

  2. WSL socat(fork) :19443 -> WSL-republished :18443 -> Envoy — the guest's
     EXACT failing hop minus QEMU (same forward.sh-style socat forwarder) —
     while THREE real Windows-driven --force-recreates (container id changed
     2ccc59->59e839->44c89->3162a7) landed inside a 16s window with four
     concurrent probers: 480 probes, 0 failures. /ready (WSL side) never dropped
     across any of the three recreates.

Conclusion: a real --force-recreate produces NO observable gap at Envoy's
passthrough listener, at the Docker published port (Windows OR WSL republish),
or through the socat forwarder. Docker Desktop's port proxy holds the published
sockets continuously across the container swap. Candidate (a) is refuted (a
host-side TLS probe succeeds within ~80ms of /ready=200 on the freshly
recreated container); candidate (b) is refuted (480/480 through the socat path
across three real recreates, no /ready drop).

That leaves exactly one component the reproduction does NOT exercise: the QEMU
guest itself and the tap/bridge between it and the WSL socat LISTEN side
(BRIDGE_IP:443). The exit-35 is therefore either specific to that guest/tap
layer, or the original 3/3 observation was a transient environmental condition
that no longer reproduces. Confirming which requires the full VM harness
(~20 min beforeAll) to instrument the guest side — not yet done.

Caveat learned the hard way: `docker compose up -d --force-recreate` issued from
WSL against this project does NOT recreate the container — Docker Desktop's
Windows daemon can't resolve the relative bind-mounts (./envoy.yaml, ...) from a
/mnt/c cwd, so the up silently no-ops and leaves the old container running. All
recreates in these experiments were therefore driven from the Windows (git-bash)
side; only the probes ran WSL-side.

UPDATE 2026-07-11 (c): guest-side instrumentation CONFIRMS the root cause
-------------------------------------------------------------------------

The full VM harness was run with a temporary probe block (S2d) that fired
un-retried `curl -v` from the guest immediately after each of six real run-proxy
restarts (credential rotation), capturing curl's exit code and the verbose TLS
trace. Result: 16 of 18 probes exit 35, one exit 56, one exit 0 — the exit-35
reproduces deterministically guest-side. Every exit-35 trace is identical:

    * IPv4: 203.0.113.1               (stub DNS -> guest DNAT -> socat -> Envoy)
    *   Trying 203.0.113.1:443...
    * TLSv1.3 (OUT), TLS handshake, Client hello (1):        (1563 bytes sent)
    * TLS connect error: ...unexpected eof while reading
    CODE=000 TCP=0.0008 TLS=0.000000 GUEST_EXIT=35

TCP connects in <1 ms (local socat accept); the ClientHello goes out; the peer
returns an immediate EOF before any ServerHello. The lone exit-56 got further —
a full handshake to the REAL pypi.org certificate, HTTP/2 GET sent, then the
same "unexpected eof" mid-response — i.e. a connection that reached a fully
serving Envoy and was then cut, consistent with the old container being killed
mid-response.

The decisive datum: waitForAdminReady returned in 1-2 ms on every iteration.
run-proxy logs "restarting proxy — credentials changed" and THEN (asynchronously)
runs `docker compose up -d --force-recreate`. The test waits for that log line,
then waitForAdminReady, then curls — with no gap. Because the OLD container keeps
answering /ready=200 throughout the swap, waitForAdminReady returns instantly
against the dying old container, and the guest curl fires straight into the
container-swap window; its ClientHello reaches a backend that is being torn down
/ not yet serving and gets an EOF.

ROOT CAUSE (confirmed): a restart/warmup race. /ready is not a valid
post-restart readiness signal, because during `docker compose up -d
--force-recreate` the OLD container answers /ready=200 until the moment it is
replaced. Any request fired between "restart requested" and "new container
actually serving" can have its TLS handshake dropped -> curl exit 35 (or exit 56
when the drop lands mid-response). Nothing to do with DNS caching, and not
guest-specific — the guest only fails because the test sequences
waitForProxyLine -> waitForAdminReady -> curl with no new-container gate.

This reconciles and CORRECTS UPDATE (b). The boundary probes there did not fail
only because they gated on the NEW container-id (waiting ~1.3 s PAST the swap)
before probing — which the real test does not. UPDATE (b)'s "candidate (a)
refuted" was an over-claim: the new container does serve passthrough within
~80 ms of ITS OWN /ready, but the real failure is that the gate never waits for
the new container in the first place. In the boundary experiments, gating on the
new container-id drove the failure rate to 0 (0/480 through the socat path
across three real recreates), so a new-container readiness gate is a verified
fix direction.

Workaround applied (interim — now REPLACED by the fix below)
------------------------------------------------------------

tests/vm/vm.test.ts had a `guestRetry()` helper (retried a guest exec up to 5
times with a 2s delay) wrapping the passthrough-to-pypi.org curl calls. This
was a test-only mitigation that papered over both symptoms without addressing
the race. It has been removed in favour of the real fix.

Fix applied 2026-07-11 (test-harness, root-cause gate)
------------------------------------------------------

Per UPDATE (c), the two symptoms were addressed at their actual causes:

  - exit 35 (restart/warmup race): added `waitForEnvoyRestart(stack, oldId,
    timeoutMs)` + `getEnvoyContainerId(stack)` to tests/proxyStack.ts. The S2/S2b
    restart tests now capture the envoy container id BEFORE triggering the
    restart and wait until the id actually changes (new container exists) AND
    that new container answers /ready — instead of plain waitForAdminReady, which
    the old container answers during the swap. This is the verified 0/480 gate.
  - exit 28 (real-network body timeout): the passthrough probes now use `curl -sI`
    (HEAD) instead of GET. pypi.org/simple/ is a ~44 MB index whose full download
    can exceed the timeout over the nested VM link; a HEAD still proves the
    passthrough TLS handshake reaches real pypi.org (200) and still triggers the
    proxy's ALLOW PASS log, without transferring the body.

With both in place, the guest probes are single and un-retried. Verified: the
full VM suite passed 23/23 on three consecutive runs (before the fix, the same
un-retried probe reproduced exit 35 at 16/18). Still test-only — run-proxy's
restart pipeline and envoyConfig.ts are untouched (see the production follow-up
below).

What's NOT done / possible follow-ups
---------------------------------------

- DONE (see UPDATE above): the DNS-cache theory was tested via the S2c probe
  and refuted — a cold cache alone does not fail; the trigger is the
  restart/warmup window. Still not done: capturing Envoy debug-level logs or
  dynamic_forward_proxy DNS cache stats *at the moment of* a real post-restart
  exit-35 failure, to pin down exactly which layer drops the handshake.
- Root cause is CONFIRMED (UPDATE c): a restart/warmup race where /ready is
  answered by the old container during the --force-recreate swap. The fix is a
  new-container readiness gate; id-gating drove the failure to 0/480. Two places
  it could live:
    - Test harness — DONE (see "Fix applied" above): waitForEnvoyRestart gates on
      the new container id + /ready; guestRetry removed; passthrough probes use
      HEAD. Verified 23/23 across three consecutive VM runs.
    - Production run-proxy (fixes it for a real workload curling right after a
      restart): recreateContainer returns without waiting for readiness, so a
      sandbox process hitting the proxy in the swap window would see the same
      exit 35. A genuine post-recreate readiness gate inside run-proxy (wait for
      the new container to actually serve) would close that window in production.
  Ruled out along the way:
    - An Envoy-internal change (worker/listener config) — not needed: the new
      container serves passthrough within ~80 ms of ITS OWN /ready (UPDATE b).
    - Docker Desktop / WSL2 port-forward re-establishment blip — not the cause:
      no /ready drop and no socat-path failure across three real recreates once
      gated on the new container (UPDATE b); Docker's port proxy holds sockets.
    - Envoy's dns_cache_config `preresolve_clusters` — not the cause (S2c): a
      cold DNS cache alone does not fail.
- The exit-28 (timeout) flakiness on the pre-existing S2 test was only
  observed intermittently (not on every run) and might be entirely separate
  from the exit-35 issue — worth keeping an eye on whether guestRetry alone
  is a durable enough fix or whether it just papers over a real latency
  problem in this test environment.
