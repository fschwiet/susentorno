# Customizable home-settings jq transforms

**Date:** 2026-07-20
**Status:** Approved (pending implementation). Revised after a codex spec review.

## Problem

The numbered VM setup scripts hard-code two jq transforms that edit settings files in
the guest's home directory:

- **VS Code settings** (`04-configure-tools.{sh,ps1}`): merges four keys into
  `~/.config/Code/User/settings.json` (Ubuntu) / `%APPDATA%\Code\User\settings.json` (Windows).
- **Claude onboarding** (`08-claude-config.{sh,ps1}`): sets `.hasCompletedOnboarding = true`
  in `~/.claude.json` on both platforms.

Because these transforms live inside the shipped scripts, a user cannot add their own
settings tweaks or change ours without editing the scripts. The goal is to pull these
transforms out into a source-controllable folder that users can freely add to and modify,
and apply them all from a single step that runs last, after network isolation.

## Goals

- Users declare settings transforms in a folder they can commit and edit to taste.
- A single numbered script, run last (after the NAT→host-only switch and reboot), applies
  every declared transform to its target file, seeding an empty `{}` when the target is
  missing.
- Ship the current two transforms as the initial defaults, extracted from the scripts.
- Consolidate the now-thinner scripts while we are in here.

## Non-goals

- No in-place migration of existing environments. Existing environments are rebuilt via
  `configamatron init`.
- No general templating or scripting language beyond jq. Transforms are jq programs.

## Source control and secrets (revised)

The `home-jq-transforms/` folder lives at `.configamatron/home-jq-transforms/`. For it to be
committable, `.configamatron/` must become partially source-controlled — today the README
tells users **not** to commit it because it holds credentials. We invert that with a bundled
ignore file:

- `init` writes a **`.configamatron/.gitignore`** (from a template) that excludes exactly the
  secret-bearing and per-environment-regenerable files, leaving everything else committable.
- Documentation changes from "do not commit `.configamatron/`" to "commit `.configamatron/`;
  the files the bundled `.gitignore` excludes are the only ones kept out of source control."

**`.configamatron/.gitignore` contents** (paths relative to `.configamatron/`):

```gitignore
# Real credentials and private keys — never commit these.
proxy/secrets/
proxy/ca/key.pem
proxy/ca/leaf-key.pem

# Per-environment credential placeholders, regenerated by init / write-github-config.
# Sanitized (no real token) but host- and environment-specific, so keep them out of the repo.
vm-shared/credentials.json
vm-shared/auth.json
vm-shared/github-config.txt
vm-shared-windows/credentials.json
vm-shared-windows/auth.json
vm-shared-windows/github-config.txt

# Regenerable build artifacts.
proxy/envoy.yaml
vm-shared-windows/dns-responder/bin
vm-shared-windows/dns-responder/obj
```

Rationale for the split, verified against the code:

- `proxy/secrets/*.yaml` hold the **real** Claude/codex/GitHub credentials
  (`write-github-config` writes the real PAT only here). Must never be committed.
- `proxy/ca/key.pem` and `proxy/ca/leaf-key.pem` are **private keys**. Public certs
  (`ca/cert.pem`, `ca/leaf-cert.pem`, the shares' `cert.pem`) are safe.
- The shares' `credentials.json` / `auth.json` / `github-config.txt` are sanitized
  placeholders (`github-config.txt` carries `ghp-SANDBOX-PLACEHOLDER`, not the real PAT), but
  they are regenerated on every `init` / `write-github-config` from host state, so they are
  ignored rather than committed.
- `proxy/envoy.yaml` is generated by `run-proxy`, and the `dns-responder` `bin`/`obj` are
  .NET build output (already filtered by `init` on copy) — all regenerable, so ignored.
- Everything else under `.configamatron/` — the numbered scripts, `home-jq-transforms/`,
  `allowlist.txt`, public certs, the bundled applier `.mjs` — is committable. (Committed
  scripts/config can go stale relative to a newer `configamatron` version; that is the user's
  call, and re-running `init` in a fresh directory always regenerates them.)

The `configamatron` tool's own root `.gitignore` still ignores `.configamatron/` for its dev
and test environments; that is independent of the end-user `.gitignore` this feature ships
inside each generated environment.

## Architecture overview

Three concerns, cleanly separated:

1. **Transform declarations** — a user-editable `home-jq-transforms/` folder (a `manifest.yaml`
   plus flat `.jq` files). Source of truth, committed to source control.
2. **One tested TypeScript core** (`src/homeJqTransforms.ts`) that parses the manifest,
   resolves per-OS target paths, and applies transforms by invoking `jq` (argv-based, no shell
   string building). The host CLI and the in-VM applier both use this code.
3. **A bundled in-VM applier** (`apply-home-jq-transforms.mjs`, produced by tsup) invoked by a
   thin numbered wrapper script. Node is available in the guest (installed at step 03), so the
   applier logic is written once in TypeScript rather than duplicated across bash and PowerShell.

### Data flow

```
.configamatron/home-jq-transforms/        <- source of truth (user edits, source-controlled)
   manifest.yaml
   vscode-settings.jq
   claude-onboarding.jq

  (init seeds, update-shares refreshes)
        |
        v
.configamatron/vm-shared/home-jq-transforms/          (visible to Ubuntu guest)
.configamatron/vm-shared-windows/home-jq-transforms/  (visible to Windows guest)

  (in the guest, step 07 runs)
        |
        v
node <script_dir>/apply-home-jq-transforms.mjs <script_dir>/home-jq-transforms
        |
        v
~/.config/Code/User/settings.json, ~/.claude.json, ...
```

The parent of `vm-shared` / `vm-shared-windows` is not mounted into the guest, so the
transforms must be physically copied *inside* each share for the guest to see them.

## File layout and manifest format

Source of truth:

```
.configamatron/home-jq-transforms/
  manifest.yaml
  vscode-settings.jq        # extracted from 04-configure-tools
  claude-onboarding.jq      # extracted from 08-claude-config
```

`.jq` files are flat, named descriptively, referenced by the manifest.

`manifest.yaml` is a top-level list of entries:

```yaml
- transform: vscode-settings.jq
  linux: ~/.config/Code/User/settings.json
  windows: "%APPDATA%/Code/User/settings.json"
- transform: claude-onboarding.jq
  linux: ~/.claude.json
  windows: ~/.claude.json
```

Entry fields:

- `transform` (required) — the **basename** of a `.jq` file in the transforms folder. Must end
  in `.jq`, must exist, and must resolve to a path contained within the transforms folder.
- `linux` (optional) — target path applied when running on Ubuntu.
- `windows` (optional) — target path applied when running on Windows.
- At least one of `linux` / `windows` must be present. Omitting one skips that transform on
  that OS (supports platform-specific transforms).

**Manifest validation** (fail loudly with a clear message on any violation):

- `transform` rejected if it is not a plain basename ending in `.jq`, if it contains path
  separators or `..`, if the resolved path escapes the transforms folder (e.g. via a symlink),
  or if the file does not exist.
- An entry with neither `linux` nor `windows` is rejected.
- A target that references an environment variable which is unset at apply time is a hard
  error (never silently expands to an empty path).

**Target path expansion** — the entire vocabulary. Expansion is performed by the TypeScript
core itself (not the OS shell), so it behaves identically on Ubuntu and Windows:

- A leading `~` or `~/` expands to the guest user's home directory (via `os.homedir()`). A
  bare `~name` (other-user form) is **not** supported and is rejected.
- `%NAME%` expands to environment variable `NAME` (a regex replace of `%NAME%` →
  `process.env.NAME`, e.g. `%APPDATA%`). This is our own portable convention, not the OS
  shell's syntax. An unset `NAME` is an error, not an empty string.

The two seeded `.jq` files reproduce the current inline transforms exactly:

`vscode-settings.jq`:

```jq
.["files.autoSave"] = "afterDelay"
| .["editor.formatOnSave"] = true
| .["editor.defaultFormatter"] = "esbenp.prettier-vscode"
| .["[csharp]"] = {"editor.defaultFormatter": "csharpier.csharpier-vscode"}
```

`claude-onboarding.jq`:

```jq
.hasCompletedOnboarding = true
```

## Core module: `src/homeJqTransforms.ts`

The single real implementation, exercised by vitest.

- `loadManifest(dir)` — read and parse `manifest.yaml`; run the full validation above. Throws
  with a clear message on malformed input.
- `resolveTarget(entry, platform, env, home)` — expand `~` / `%NAME%` for the given platform's
  target. Returns `null` when the entry has no target for that platform; throws on an unset
  variable or an unsupported `~name` form.
- `applyTransforms({ dir, platform, ... })` — process entries **in manifest order** (so two
  entries targeting the same file compose predictably). For each entry with a target for
  `platform`:
  - Read the target. If it is missing or **not parseable as JSON**, seed the jq input with `{}`.
    A target that is valid JSON but the wrong shape (array/scalar) is passed through as-is;
    jq then fails on it and the write is skipped (see below).
  - Run the transform via an injectable, argv-based jq runner:
    `run('jq', ['-f', <absolute transform path>], { input })` — no shell string concatenation,
    so paths and spaces are safe and there is no injection surface.
  - On jq success, write the result **atomically** (temp file + rename), creating parent
    directories as needed. On jq failure, leave the target untouched and record the error.
  - Returns a per-file result list (target path, created-vs-updated, ok/error with stderr).
- `previewTransforms(dir)` — run each transform against `{}` via the same runner and return
  `{ transform, linuxTarget, windowsTarget, output | error }` for host-side display.

`applyTransforms` and `previewTransforms` before running anything verify that the `jq` binary
resolves; a missing `jq` yields an actionable error rather than an opaque spawn failure.

## In-VM applier: `src/vmApplyHomeJqTransforms.ts`

Thin entrypoint: parse argv (the transforms directory), verify `node`/`jq` are usable, detect
platform via `process.platform` (`win32` → Windows targets, else Linux targets), call
`applyTransforms`, print a summary, and exit non-zero if any transform failed.

**Build and delivery** (hardened after review):

- tsup gets an explicit second entry that bundles this file (with the `yaml` dependency
  **inlined**, not left external) into a standalone `apply-home-jq-transforms.mjs`.
- The build emits the bundle into both `templates/vm-shared/` and
  `templates/vm-shared-windows/`. These are gitignored build artifacts (like `dist/`).
- A `prepublishOnly` / `prepack` build guarantees the bundle exists before packing, and a
  packaging test asserts the bundle is present in `pnpm pack --dry-run` output and that an
  `init` from the packed layout produces a runnable share (so a missing artifact fails CI,
  never a user's VM).
- `init` carries the bundle into an environment when it copies the template share dirs.

## Wrapper scripts (path-safe)

`07-apply-home-jq-transforms.{sh,ps1}` resolve paths relative to the script, not the caller's
working directory (important when run from a UNC share):

- Bash: derive `script_dir` from `${BASH_SOURCE[0]}` and call
  `node "$script_dir/apply-home-jq-transforms.mjs" "$script_dir/home-jq-transforms"`.
- PowerShell: use `$PSScriptRoot` and
  `& node (Join-Path $PSScriptRoot 'apply-home-jq-transforms.mjs') (Join-Path $PSScriptRoot 'home-jq-transforms')`.

## Script consolidation and new run order

The two *home-settings* jq blocks are **deleted** from `04-configure-tools` (VS Code) and
`08-claude-config` (claude onboarding); that work moves to the new final applier step. The
Firefox-policy jq merge in `06-trust-ca` targets a system path (`/etc/firefox/policies`), not
a home dotfile, and stays in the script.

Ubuntu's `gh` install moves from the github-auth script into `01-apt-packages.sh` (added to
the existing `apt install` line), mirroring Windows (which installs `GitHub.cli` in step 01)
and ensuring `gh` is installed while NAT still provides full apt access — before isolation.

Scripts are renumbered and combined:

- **`05-configure-network.{sh,ps1}`** = old `06-trust-ca` + old `07-setup-persistence`
  (Ubuntu) / `07-setup-network` (Windows). Trusts the CA first, then installs dnsmasq +
  egress/netplan (Ubuntu) or the DNS responder (Windows). Runs pre-isolation.
  - Bash usage: `05-configure-network.sh <host-ip> [cert-path]` (cert defaults to `cert.pem`
    beside the script).
  - PowerShell usage: `.\05-configure-network.ps1 -HostIp <ip> [-CertPath <path>]`, retaining
    `#Requires -RunAsAdministrator` (both source scripts require admin).
- **`06-auth-config.{sh,ps1}`** = old `05-github-auth` (minus the `gh` install, now in step 01)
  + old `08-claude-config` (minus its jq block) + old `09-codex-config`. No args; reads
    `github-config.txt` beside it. Does gh/git auth, the claude credential symlink/copy, and
    the codex credential symlink/copy. Runs post-reboot. Placing the claude credential here,
    before onboarding is set in step 07, is fine: this script never invokes `claude`.
- **`07-apply-home-jq-transforms.{sh,ps1}`** — the path-safe wrapper above. Runs post-reboot,
  last. Limited to `node` + local `jq`; it makes no network calls and triggers no
  package-manager/tool initialization, so it is unaffected by network isolation.

Final run order (both platforms), fully sequential:

| Step | Script | Args | When |
|---|---|---|---|
| 1 | 01-packages *(Ubuntu: + gh)* | | pre-isolation |
| 2 | 02-pnpm | | pre-isolation |
| 3 | 03-tools | | pre-isolation |
| 4 | 04-configure-tools *(VS Code jq removed)* | | pre-isolation |
| 5 | **05-configure-network** | `<host-ip> [cert-path]` / `-HostIp -CertPath` | pre-isolation |
| — | **switch NAT→host-only + reboot** | | |
| 6 | **06-auth-config** | | post-reboot |
| 7 | **07-apply-home-jq-transforms** | | post-reboot, last |

Moving claude's onboarding write from step 08 to the final step is safe: nothing between
(github auth, credential placement) requires the claude CLI to be onboarded. `node` and `jq`
are both installed before step 07 (steps 03 and 01).

## CLI changes

### `init`

- `templates/` gains a `home-jq-transforms/` folder (manifest + the two extracted `.jq` files)
  and a `configamatron.gitignore` template written to `.configamatron/.gitignore`.
- `initEnvironment` copies `home-jq-transforms/` to `.configamatron/home-jq-transforms/`
  **and** seeds a copy into both `vm-shared/home-jq-transforms/` and
  `vm-shared-windows/home-jq-transforms/`, so a freshly initialized environment is runnable
  without a manual `update-shares` step.
- `init` writes `.configamatron/.gitignore`.
- `init`'s "next steps" output notes that transforms are customizable, that `update-shares`
  refreshes the shares after edits, and that `.configamatron/` (minus the ignored secrets) is
  intended for source control.

### `update-shares` (new command)

Refreshes the share copies after a user edits transforms.

1. Require `.configamatron` (standard missing-environment error otherwise); load and validate
   the manifest; verify `jq` is available on the host (clear install-jq message otherwise).
2. **Preview**: for each transform, print its name, resolved `linux` and `windows` target
   paths, and the result of applying it to `{}`. Both platforms are shown because the host
   does not know which guest will consume the transforms. A jq error in a `{}` preview is
   fatal and blocks the copy — this catches syntax and empty-object-runtime errors, though it
   is **validation, not a guarantee** that the transform will succeed against every real guest
   file (the per-target atomic write is the actual safety net in the guest).
3. Copy `home-jq-transforms/` into each share using **stage-then-swap**: copy into a sibling
   staging directory, then replace the live share copy only after staging succeeds; clean up
   staging on failure. This ensures an interrupted `update-shares` never leaves a guest with a
   half-updated or empty transforms folder. List the files copied.
4. `-n` / `--dry-run`: preview only, no copy.

## Edge cases

- **Missing / empty target file** — seeded with `{}`, then transformed (creates parent dirs).
- **Unparsable target file** — treated as `{}` (matches current script behavior).
- **Valid JSON but wrong shape** (array/scalar) — passed to jq unchanged; jq fails and the
  target is left intact (matches current inline behavior, which errors rather than clobbering).
- **Invalid jq program** — the in-VM applier fails loudly (non-zero exit) for that transform;
  `update-shares` blocks the copy when the `{}` preview errors.
- **Two entries targeting the same file** — applied in manifest order, each reading the prior
  result.
- **Entry with no target for the current platform** — skipped on that platform.
- **Unset variable / unsupported `~name`** — hard error at resolve time.
- **`node` or `jq` missing in the guest** — the applier verifies both and prints an actionable
  error. (jq is installed at step 01, node at step 03.)
- **jq missing on host** — `update-shares` exits with a clear install-jq message.

## Testing

- **Unit (vitest, stubbed jq runner):**
  - manifest parse/validate: valid; malformed YAML; missing `.jq` file; entry with no target;
    path traversal (`../x.jq`, absolute path, separator in `transform`).
  - `resolveTarget`: `~` / `~/` and `%APPDATA%` expansion for both platforms; `null` when no
    target; error on unset `%NAME%`; rejection of `~name`.
  - `applyTransforms`: seeds `{}` for a missing target; treats unparsable as `{}`; leaves a
    valid-but-wrong-shape target intact when jq fails; merges into an existing object; writes
    atomically; creates parent directories; applies two same-target entries in order.
  - `previewTransforms`: output shape; error captured per transform.
- **Integration (real jq):** apply both seeded defaults to temp files and assert the results
  match the JSON the old inline scripts produced; execute the packaged `.mjs` end-to-end.
- **Command / packaging tests:** `update-shares` stages-then-swaps into both shares and
  dry-run copies nothing; `update-shares` blocks the copy on a jq error; `init` seeds all three
  transform locations and writes `.configamatron/.gitignore`; `pnpm pack --dry-run` includes
  the bundled applier; wrapper path-resolution behaves correctly on both shells.
