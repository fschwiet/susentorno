# `create-host-network` / `delete-host-network`

## Purpose

`setup-machine.md` today has two manual, host-level steps done once per Windows host, before any environment exists: (1) create a Hyper-V Internal switch and assign it a static host IP by hand, and (2) run `templates/proxy/host-allow-vm-inbound.ps1` — a script templated into every environment's `.susentorno/proxy/` by `susentorno init`, even though its effect is host-wide, not per-environment — to open the firewall.

This design replaces both with two CLI commands, `susentorno create-host-network` and `susentorno delete-host-network`, following the pattern `setup-guest-unix` already established for elevated Hyper-V/PowerShell automation from this CLI (pure command-string builders, a thin untested `PowerShellExec` wrapper, an `isElevated()` gate checked first). `host-allow-vm-inbound.ps1` is deleted outright — the underlying decision, including the `--isolation-name` sandboxing mechanism and the new real-Hyper-V test tier this enables, is recorded in [ADR-0023](../../adr/0023-cli-owned-host-network-with-real-hyperv-tier.md).

Proactively detecting Default Switch IP drift (as opposed to recovering from it, which this design covers) is tracked separately as [issue #83](https://github.com/fschwiet/susentorno/issues/83) — deliberately left open where it should live.

## Scope

Both commands are host-level: unlike `setup-guest-unix`, they do not require an environment directory (`requireEnvPathsOrExit` does not apply) and run before any environment exists, matching where `setup-machine.md` sits relative to `setup-environment.md` today.

Both require an elevated terminal. This is checked in the CLI glue layer (`src/commands/createHostNetwork.ts`/`deleteHostNetwork.ts`), before any prompting or call into the orchestration modules — the same division `setup-guest-unix` already uses (elevation lives in `src/commands/setupGuestUnix.ts`, not in `src/guestSetup/*.ts`). The orchestration modules below (`createHostNetwork`/`deleteHostNetwork`) assume an elevated context and do not re-check it themselves.

Every validation or existence-check failure path (not just mutation failures) sets `process.exitCode = 1` and returns without proceeding further — matching this project's existing convention throughout `src/commands/*.ts`.

## Naming and `--isolation-name`

The switch name is fixed by default: `susentorno-internal`, derived via the existing `deriveSwitchName()` (`src/guestSetup/switchName.ts`) applied to the existing `DEFAULT_INTERNAL_SWITCH_ADAPTER` constant (`vEthernet (susentorno-internal)`, `src/runHosting/forwarder.ts`) — that constant names the *adapter alias*, not the switch itself, so `hostNetworkNames.ts` derives the base switch name from it via `deriveSwitchName` rather than hardcoding a second literal.

An optional `--isolation-name <name>` flag (both commands) renames the switch to `susentorno-<name>-internal` and its adapter alias to `vEthernet (susentorno-<name>-internal)`. Every firewall rule's `DisplayName` gets the same treatment — `susentorno` becomes `susentorno-<name>` throughout:

| Rule | Default `DisplayName` | With `--isolation-name test` |
| --- | --- | --- |
| TCP 80/443 | `susentorno Envoy Proxy (VM inbound)` | `susentorno-test Envoy Proxy (VM inbound)` |
| UDP 53 | `susentorno DNS stub (VM inbound)` | `susentorno-test DNS stub (VM inbound)` |
| UDP 67 | `susentorno DHCP (VM inbound)` | `susentorno-test DHCP (VM inbound)` |
| TCP 445 (both adapters) | `susentorno share (VM inbound)` | `susentorno-test share (VM inbound)` |

`--isolation-name` is validated against a narrow safe character set (letters, digits, hyphens only — no `*`, `?`, `[`, `]`, or other characters PowerShell's `-Name`/`-DisplayName` wildcard matching treats specially) before it's used anywhere. This matters beyond cosmetics: `Get-VMSwitch -Name` and `Get-NetFirewallRule -DisplayName` both perform wildcard-tolerant matching, so every existence/deletion query built from a derived name (switch existence, the interface sweep, the named SMB sweep) filters its parsed results down to an **exact** match against the expected literal string before acting — the same defensive pattern `hyperVQueries.ts`'s `parseGetVmResult` already uses for `Get-VM -Name` ("only an entry whose `Name` equals the input exactly counts"). Without this, a switch or rule set could be silently misidentified — a real risk for a command whose whole job includes deleting things by name.

This mechanism exists purely so the `host-network` test tier (below) can create and delete its own network (`susentorno-test-internal`) without touching a developer's real `susentorno-internal` switch — both can coexist on the same machine. It is not a general multi-network feature; nothing else in the system (run-hosting, guest setup scripts) is parameterized to talk to a non-default host network today. It is also not a *complete* isolation guarantee — two things are explicitly shared with production regardless of `--isolation-name`, so "sandboxed" below means "the switch and its own firewall rules are separate," not "nothing is shared":

- **The dedicated node.exe copy** (`getDedicatedNodePath`, `src/runHosting/relaunchViaDedicatedNode.ts`) that the TCP/DNS/DHCP rules are `-Program`-scoped to. There is exactly one such copy, host-wide — a production and an isolated test rule set both reference the same path, and both `create-host-network`'s stale-rule cleanup and `delete-host-network`'s Query-User sweep (below) act on that shared path regardless of `--isolation-name`.
- **The Default Switch (NAT) adapter itself.** It's a real, shared Windows/Hyper-V object this project never creates or deletes; only the `DisplayName` of the SMB rule's NAT-side half varies with `--isolation-name`, not the adapter it's scoped to.

## `create-host-network`

Flags: `--isolation-name <name>` (optional, validated as above), `--subnet <n>` (optional, 0–255, skips the interactive prompt), `--nat-adapter-alias <alias>` (optional, default `vEthernet (Default Switch)`, needed for the SMB rule's NAT-side half).

1. **Existence check.** `Get-VMSwitch -Name <switch-name> -ErrorAction SilentlyContinue`, parsed structurally and filtered to an exact name match (empty/non-matching output = not found — not a failure, the same convention `hyperVQueries.ts`/`preflightChecks.ts` already use for `Get-VM`/`Get-VMSwitch`).
2. **NAT adapter validation.** Resolve the NAT adapter's current IPv4 via `resolveForwardListenAddress(<nat-adapter-alias>)` (`src/runHosting/forwarder.ts` — reads `os.networkInterfaces()` in-process, no PowerShell round-trip). Fail cleanly here if it has none, *before* touching Hyper-V at all — mirroring `host-allow-vm-inbound.ps1`'s existing "resolve and validate every address up front" approach, so a resolution failure can't leave rules deleted and not yet replaced.
3. **Branch on the existence check:**
   - **Switch already exists:** skip switch/IP creation and the subnet prompt entirely. Resolve the switch's current host IPv4 via `resolveForwardListenAddress(<adapter-alias>)`. If it has none (a prior partial failure), fail with a message saying so rather than proceeding with a missing address. Otherwise, jump straight to step 6 (stale-rule cleanup) using this existing host IP and the NAT IP from step 2 — this is the "refresh the firewall rules" path, restoring the "safe to rerun after a Default Switch IP change" property `host-allow-vm-inbound.ps1` has today, without recreating the switch or weakening any rule's `-LocalAddress` scoping. Print a message distinguishing this from a fresh create, e.g. `create-host-network: switch '<switch-name>' already exists at <ip> — refreshing its firewall rules only.`
   - **Switch does not exist:** continue to step 4.
4. **Resolve the subnet's third octet.**
   - If `--subnet <n>` was passed, use it directly (still validated against the taken-list below — fails loudly on collision, since no interactive fallback exists).
   - Otherwise, read every IPv4 address currently configured on any local adapter via `os.networkInterfaces()` (same in-process source `resolveForwardListenAddress` reads), and for each, compute the taken range using its actual netmask (not a naive third-octet-only comparison — an address with, say, a `/16` mask collides with every `192.168.n.0/24` in that block, not only the one matching its literal third octet). Compute the lowest `n` in 0–255 whose `192.168.n.0/24` doesn't overlap any detected range, and prompt (`promptText`) for `Subnet (192.168.<n>.x)` with that as the suggested default. If no `n` in range is free (exceedingly unlikely, but not impossible), fail cleanly with a message saying so rather than looping or picking a colliding one. An input that fails validation (out of range, or colliding with a taken range) re-prompts rather than silently proceeding.
5. `New-VMSwitch -Name <switch-name> -SwitchType Internal`, then `New-NetIPAddress -InterfaceAlias <adapter-alias> -IPAddress 192.168.<n>.1 -PrefixLength 24`.
6. **Stale-rule cleanup.** Clear any existing rule with each of the four `DisplayName`s this command is about to (re)create — matching `host-allow-vm-inbound.ps1`'s existing behavior of removing before recreating, so a rerun never leaves a duplicate or an outdated rule alongside a fresh one. Also clear any stale Windows "Query User"-prompt rule for the dedicated node.exe path (not isolation-scoped — see above).
7. **Create the four firewall rule sets**, ported from `host-allow-vm-inbound.ps1`'s logic to TypeScript command builders (see Module layout): TCP 80/443 + UDP 53, both `-Program`-scoped to the dedicated node.exe path and `-LocalAddress`-scoped to the host IP; UDP 67, interface-scoped only (DHCP broadcast has no destination address to scope to — the one deliberate exception to `-LocalAddress` scoping, unchanged from today); TCP 445 on both `<adapter-alias>` and `--nat-adapter-alias`, each `-LocalAddress`-scoped to that adapter's own IP — the NAT-side half keeps its `-LocalAddress` scoping exactly as today; it is not weakened to an interface-only rule (that was considered and rejected — see "Considered and rejected" below).
8. Print the host IP and a short "what's next" pointer, replacing today's script's closing `Write-Host` lines.

### Considered and rejected: dropping `-LocalAddress` from the NAT-side SMB rule

Scoping that rule by `-InterfaceAlias` alone (like the DHCP rule) would make it immune to Default Switch IP drift without needing the refresh path above. Rejected: `host-allow-vm-inbound.ps1`'s own comments explain `-LocalAddress` exists specifically so the firewall boundary holds even if Windows' strong-host model is ever weakened (an interface-only rule permits a packet to *any* local address on that port) — a scenario [ADR-0003](../../adr/0003-transparent-interception-and-network-isolation-boundary.md) and a prior investigation (`docs/investigations/2026-07-23-host-model-lets-guest-reach-other-host-ips.md`, referenced there) treat as real, not theoretical. DHCP is the one existing exception, and only because a DHCP client's broadcast source has no fixed destination address to scope to — a technical necessity, not a convenience. SMB has no such constraint, so weakening its scoping to solve an IP-drift inconvenience would trade a real security boundary for a rare, narrow annoyance. The refresh path in step 3 above solves the actual problem without that trade.

## `delete-host-network`

Flags: `--isolation-name <name>` (optional, same validation as `create-host-network`). No `--nat-adapter-alias` — the NAT-side SMB rule is found by name, not by interface (below), so it needs no adapter parameter.

This command is deliberately a "return this adapter to a pristine state" tool, not a strict undo of what a matching `create-host-network` made — the sweeps below remove rules regardless of who created them, so it can also clean up a corrupted host where unrelated rules have accumulated on the adapter.

1. **VM-attachment check.** Before touching anything, check whether any VM currently has a network adapter connected to `<switch-name>` (`Get-VMNetworkAdapter | Where-Object SwitchName -eq <switch-name>`, or equivalent). If any are found, fail with a message naming them and telling the user to detach or stop those VMs first, rather than proceeding — this project does not assume `Remove-VMSwitch`'s own behavior toward an in-use switch is safe to rely on unverified, so the check is explicit rather than assumed.
2. **Interface sweep.** Every firewall rule whose interface filter matches `<adapter-alias>` is removed, regardless of `DisplayName` — including the DHCP rule (interface-scoped, no `-LocalAddress`).
3. **Query-User sweep.** Every stale Windows "Query User"-prompt rule for the dedicated node.exe path is removed, matched the same way `create-host-network`'s cleanup matches them (by name pattern and program-path suffix — these rules are typically *not* interface-scoped, so step 2's interface filter does not catch them).
4. **Named sweep.** Every firewall rule named `<rule-prefix> share (VM inbound)` is removed regardless of adapter — this is what catches the SMB rule's Default-Switch/NAT-adapter half, which step 2's interface filter deliberately does not touch.
5. **Switch removal.** `Get-VMSwitch -Name <switch-name>`, exact-matched; if found, `Remove-VMSwitch` (its IP assignment goes with it — no separate step). If not found, this is a no-op, not an error.
6. Print a summary of what was actually removed (switch: yes/no; rule counts per sweep).

Steps 2–5 are each attempted independently of the others' outcome — a rerun after a partial failure, or against an already-clean host, just finishes whatever's left rather than requiring a prior step to have succeeded. This is a deliberate exception to the stop-on-first-mutation-failure rule below: within step 2's and step 4's sweeps specifically, each individual rule removal is attempted (best-effort), not aborted after the first failure, and step 6's summary reports anything that couldn't be removed. `delete-host-network` exits non-zero only if something it attempted to remove genuinely could not be removed — never solely because there was nothing to do.

## Error handling

Two different PowerShell call shapes need different treatment, matching the split `hyperVQueries.ts` (queries) vs. `hyperVOperations.ts`/`vmReconcile.ts` (mutations) already use — with one addition this design needs that existing callers haven't: the shared `PowerShellExec` interface (`src/guestSetup/powerShellExec.ts`) returns only `{ exitCode, stdout }` — `createRealPowerShellExec` calls `execa` with `reject: false` and never captures stderr. That means an uncaught PowerShell error's message is not visible to this project's code today, only its exit code.

- **Query commands** (`Get-VMSwitch`, `Get-NetFirewallRule`, `Get-VMNetworkAdapter`) are built with `-ErrorAction SilentlyContinue` and read via **parsed stdout**, not exit code — empty/non-matching output means "not found," meaningful information the orchestration acts on (proceed with creation; skip a removal step), never a reason to abort the whole command. (IP/subnet lookups don't hit any of this — they're in-process `os.networkInterfaces()` reads, not PowerShell calls.)
- **Mutating commands** (`New-VMSwitch`, `New-NetIPAddress`, `New-NetFirewallRule`, `Remove-VMSwitch`, `Remove-NetFirewallRule`) explicitly pass `-ErrorAction Stop` and are wrapped in PowerShell-side `try { <cmdlet> } catch { Write-Output "ERROR: $($_.Exception.Message)"; exit 1 }` — routing the failure message through **stdout** (which `PowerShellExec` does capture) rather than depending on stderr or on a given cmdlet's own default error-action behavior, which isn't uniformly terminating across the Hyper-V/NetSecurity module cmdlets used here. A caught failure prints `create-host-network: <message>` / `delete-host-network: <message>`, sets `process.exitCode = 1`, and — in `create-host-network` — stops immediately rather than continuing to later steps, since its steps have real ordering dependencies (creating firewall rules for a switch that failed to create makes no sense). `delete-host-network`'s steps 2–5 are the deliberate exception described above.

## Module layout

New `src/hostNetwork/` folder, mirroring the existing `src/guestSetup/` split (pure builders/parsers, unit-tested directly; orchestration composed from them, unit-tested with fakes; the actual `execa` call is the existing untested `PowerShellExec` wrapper, reused as-is):

| File | Responsibility |
| --- | --- |
| `src/hostNetwork/hostNetworkNames.ts` | Validates `isolationName`; derives `switchName`/`adapterAlias`/every rule `DisplayName` from it (or the default, unnamed case via `deriveSwitchName(DEFAULT_INTERNAL_SWITCH_ADAPTER)`). |
| `src/hostNetwork/subnetSelection.ts` | Detects taken `192.168.n.0/24` ranges from `os.networkInterfaces()` (injectable, same convention `resolveForwardListenAddress` uses), netmask-aware; computes the lowest free `n`; validates a given `n`. |
| `src/hostNetwork/hostNetworkOperations.ts` | Command builders for `New-VMSwitch`, `New-NetIPAddress`, the four firewall rule sets (each wrapped per the `-ErrorAction Stop`/try-catch convention above), the stale-named-rule and Query-User cleanups, `Remove-VMSwitch`, the interface-scoped sweep, and the named sweep. |
| `src/hostNetwork/createHostNetwork.ts` | Orchestrates the create flow (steps 1–8 above, including the existing-switch refresh branch) against injected `PowerShellExec`/prompt/query dependencies. Assumes elevation was already checked by its caller. |
| `src/hostNetwork/deleteHostNetwork.ts` | Orchestrates the delete flow (steps 1–6 above), including the VM-attachment check. Assumes elevation was already checked by its caller. |
| `src/commands/createHostNetwork.ts` | Thin CLI glue: elevation gate, prompt, call `createHostNetwork`, print results. Registered in `src/cli.ts`. |
| `src/commands/deleteHostNetwork.ts` | Thin CLI glue: elevation gate, call `deleteHostNetwork`, print results. Registered in `src/cli.ts`. |

Reused as-is, no duplication: `isElevated`/`elevationCheck.ts`, `createRealPowerShellExec`/`powerShellExec.ts`, `quoteForPowerShell`, `promptText` (`cliPrompt.ts`), `buildGetVmSwitchCommand` (`hyperVQueries.ts` — its query is reused; a new `parseVmSwitchExistsExact` parses the result, since the shared `parseVmSwitchExists` only checks "some output came back," not an exact name match), `deriveSwitchName` (`switchName.ts`), `resolveForwardListenAddress` (`runHosting/forwarder.ts`), and `getDedicatedNodePath` (`relaunchViaDedicatedNode.ts`).

## Testing

**Unit tier** (`tests/unit/hostNetwork/`): every command builder/parser above, plus the netmask-aware subnet-detection algorithm (given a set of local IPv4 addresses and netmasks, which `n` values are taken, including a broader-prefix collision like a `/16` address; lowest-free-`n` computation; out-of-range/taken-collision rejection; the all-256-taken failure case), the isolation-name validation (rejecting wildcard-special characters) and name derivation (default vs. `--isolation-name test`, including that the NAT-adapter alias and dedicated-node.exe path are unaffected by it), and `create-host-network`'s existing-switch refresh branch (given a switch already exists, the right steps are skipped and the right ones run).

**New `host-network` tier** (`pnpm test:host-network`, `tests/host-network/`, `vitest.host-network.config.ts`), per [ADR-0023](../../adr/0023-cli-owned-host-network-with-real-hyperv-tier.md): runs `create-host-network`/`delete-host-network` against real Hyper-V and real Windows Firewall state, always passing `--isolation-name test`, so it has free reign over `susentorno-test-internal` without touching a developer's real `susentorno-internal` (subject to the shared-state caveats noted under `--isolation-name` above). The subnet it uses is computed by calling `subnetSelection.ts`'s detection function directly (in-process, since it's a pure function) rather than hardcoding a value, so the tier can't collide with whatever happens to be free on the machine it runs on.

A startup gate checks `isElevated()` and fails fast (not skip-silently) if not admin, matching the existing "a missing live-tier prerequisite is an environmental failure" philosophy `proxy-stack`/`guest` already establish. `vitest.host-network.config.ts` sets `fileParallelism: false`, matching `vitest.proxy-stack.config.ts`/`vitest.guest.config.ts`'s existing precedent for tiers that manipulate shared, non-namespaced host state. Each test calls `delete-host-network --isolation-name test` in a `beforeEach` for a guaranteed-clean starting point, and again in an `afterEach`/`afterAll` so a failed assertion doesn't leave `susentorno-test-internal` behind for the next run. Assertions against created state go through the same filter-level detail `verify-proxy.ps1`'s existing `Test-RuleTuple`/`Test-RuleSet` helpers already check (protocol, port, interface, address, program, enabled/direction/action) rather than just confirming a rule with the right name exists — reusing that logic (or a TypeScript equivalent driven the same way) rather than a shallower check, so the tier actually substantiates the coverage claim [ADR-0023](../../adr/0023-cli-owned-host-network-with-real-hyperv-tier.md) makes. Wired into the default `pnpm test` pipeline alongside `guest` — a full green run now also requires an elevated shell.

## Documentation updates

- `templates/proxy/host-allow-vm-inbound.ps1` is deleted. No separate copy-step code change is needed: `initEnvironment()` (`src/initEnv.ts`) copies the entire `templates/proxy` directory in one `cpSync` call, not file-by-file, so deleting the template is sufficient on its own. `tests/unit/templates.test.ts` and `tests/unit/initEnv.test.ts`, which currently assert this file is present after `init`, need updating to match.
- `setup-machine.md` §1–2 collapse into one step: run `susentorno create-host-network` from an Administrator PowerShell. The existing "One host IP, used everywhere" and "Two host addresses, only one stable" callouts are unaffected — they describe the host IP's role elsewhere in the system, not how it's created. `delete-host-network` is documented as the reset path, and the refresh-on-rerun behavior is documented as the answer to "the Default Switch's IP changed."
- `setup-environment.md` loses its "if this is the first environment you've set up on this machine, also open the host firewall now" callout entirely — firewall setup has no per-environment trigger anymore. It also loses its separate manual `New-NetFirewallRule` block for SMB (445) under "Enable shared drives": that block was already redundant with (and inconsistently scoped compared to — no `-LocalAddress`, no NAT-adapter half) the SMB rule `host-allow-vm-inbound.ps1` created; now that `create-host-network` is the single, correctly-scoped source of that rule, the duplicate manual block is removed rather than left as a confusing second path.
- `setup-guest.md` still directly instructs running `powershell -File .susentorno\proxy\host-allow-vm-inbound.ps1` — updated to `susentorno create-host-network`.
- `src/commands/init.ts` drops its printed `(Windows) admin PowerShell: powershell -File .susentorno/proxy/host-allow-vm-inbound.ps1` next-step line.
- `verify-proxy.ps1`'s references to `host-allow-vm-inbound.ps1` (WARN hint text and explanatory comments) are updated to point at `susentorno create-host-network`; its rule-matching logic is unaffected since the same fixed `DisplayName`s are preserved by default (an isolation-named network is never what `verify-proxy.ps1` checks — it always verifies the default, production names).
- `testing.md` gains a fifth tier row (`host-network`) in its tier table and prerequisites table, and its "avoid creating new tiers" guidance gets a pointer to [ADR-0023](../../adr/0023-cli-owned-host-network-with-real-hyperv-tier.md) as the recorded exception. `development.md`'s Verification Pipeline step list gains the new tier alongside `guest`.
- `src/guestSetup/powerShellExec.ts`'s comment describing the real wrapper as "exercised only by manual verification" is updated — once the `host-network` tier exists, it's exercised by that automated tier too (it still has no dedicated unit test of its own, unchanged).

## Out of scope

- **General multi-network support.** `--isolation-name` exists for test sandboxing; nothing else in the system (run-hosting, guest setup) is parameterized to address a non-default host network.
- **Changing what the firewall rules allow**, beyond the refresh-on-rerun behavior described above. This design changes *who creates* the rules, *how cleanly they can be torn down*, and *how a rerun behaves against an existing switch* — not the rules' scope or the ports/protocols they admit, which remains exactly what `host-allow-vm-inbound.ps1` already enforces, per [ADR-0003](../../adr/0003-transparent-interception-and-network-isolation-boundary.md).
- **Proactive detection of Default Switch IP drift** — tracked as [issue #83](https://github.com/fschwiet/susentorno/issues/83), left for a future change to place.
