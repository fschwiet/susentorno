# Automate Ubuntu guest isolation and post-scripts

## Purpose

`susentorno setup-guest-unix` (see [2026-08-06-automate-ubuntu-guest-setup-design.md](2026-08-06-automate-ubuntu-guest-setup-design.md)) automates mounting the SMB share and running `pre-scripts/` on an Ubuntu guest, but stops before network isolation — that design's "Out of scope" section explicitly flagged isolation, the post-isolation address change, and `post-scripts/` as needing their own design, since the DHCP-wait uncertainty around isolation deserves deliberate treatment.

The gap this closes: after a guest is isolated (its adapter reassigned from the Default Switch to the Internal switch), its `/etc/fstab` entry still points at the old, now-unreachable Default-Switch host IP, so the SMB mount silently breaks. Nothing today updates it, and nothing automates isolation or `post-scripts/` either — a user still has to hand-drive `Stop-VM`/`Connect-VMNetworkAdapter`/`Start-VM`, fix the mount, and run two more scripts by hand, exactly the copy-paste-heavy, error-prone pattern `setup-guest-unix` was built to eliminate for the phase before it.

This design extends `setup-guest-unix` itself (rather than adding a second command) to cover the entire remaining Ubuntu flow: isolation, the post-isolation mount fix, and `post-scripts/`. After this change, `setup-guest.md`'s Ubuntu path is "install `openssh-server`, then run `susentorno setup-guest-unix`" — nothing manual left except VM creation (§1) and the one-time host firewall setup.

## Why the mount isn't just pointed at the isolated IP from the start

It was tested and confirmed that a guest still attached to the Default Switch (NAT/setup phase) can, on at least one host, successfully reach the Internal-switch host IP directly — which would seem to make the whole isolation-phase mount problem moot by mounting there from the very first step. This isn't adopted as the design, for a specific, previously-documented reason:

This project has already investigated exactly this class of behavior (a now-removed `docs/investigations/2026-07-23-host-model-lets-guest-reach-other-host-ips.md`, still visible in git history at commit `41caed6`). A guest confined to one adapter of a multi-homed Windows host reaching the host's *other* adapter IP, on an allowed port, depends entirely on the host's networking model — specifically Windows' "weak host receive" setting and inter-interface forwarding — neither of which this project sets or asserts. That investigation found the pivot **not reachable** on the host it measured (strong-host, no forwarding, both Windows defaults at the time); a guest reaching the Internal-switch host IP from the Default Switch today indicates that host-model state differs now, for reasons not further diagnosed here. `host-allow-vm-inbound.ps1` already scopes its SMB firewall rule with `-LocalAddress` specifically to narrow this class of exposure, citing that same investigation — building new automation that *depends on* cross-adapter reachability working would run counter to that existing hardening effort.

The mount therefore continues to use the Default-Switch host IP during the pre-isolation phase (unchanged from the existing `mountShare` design) and is explicitly re-pointed at the Internal-switch host IP once isolation has actually happened — a guaranteed-reachable address in both phases, with no dependency on undocumented host networking defaults.

## Scope

`setup-guest-unix` becomes the single command covering the entire Ubuntu path from "SSH is reachable" through "the guest is fully set up," replacing today's "run `setup-guest-unix`, then hand-drive isolation, the mount fix, and `post-scripts/`" split. Windows-guest automation remains out of scope, unchanged from the original design.

## New prerequisite: elevation

`Get-VMNetworkAdapter`, `Stop-VM`, `Connect-VMNetworkAdapter`, and `Start-VM` all require an elevated process token — confirmed directly: `Get-VMNetworkAdapter` against a real VM from a non-elevated shell fails with "You do not have the required permission to complete this task," while `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)` cleanly reports `False`/`True` with no special permission of its own. A Node CLI has no good way to silently self-elevate (shelling out to `Start-Process -Verb RunAs` would trigger an interactive UAC dialog and hand off to a disconnected window, breaking the inherited-stdio design every SSH/PowerShell invocation in this command relies on), so `setup-guest-unix` now requires being launched from an already-elevated terminal — the same requirement `setup-machine.md` already documents for `host-allow-vm-inbound.ps1`.

The command checks this first, before anything else (including prompting): run the `IsInRole` check via the same `execa`-to-`powershell.exe` pattern used throughout, and exit immediately with "re-run this from an Administrator PowerShell/terminal" if it's not elevated.

## New input: VM name

None of today's prompts (guest address, username, share/account name, password) let the command identify the guest as a **Hyper-V VM** — `Stop-VM`/`Connect-VMNetworkAdapter`/`Start-VM`/`Get-VMNetworkAdapter` all key off the VM's Hyper-V name, which has no necessary relationship to the guest OS's own hostname. This becomes a new required prompt, asked alongside the existing ones. Consistent with the original design's choice not to persist guest address/username across runs, the VM name is prompted fresh every run too — no config file to introduce or go stale.

Before any destructive operation (the first `Stop-VM`), the command validates: `Get-VM -Name <name>` resolves to exactly one VM whose `Name` matches the input exactly (a typo must fail loudly, not silently act on the wrong guest, or match unexpectedly broadly — `Get-VM -Name` accepts wildcard patterns, so a resolved result is checked against the literal input string rather than trusted as-is), and `Get-VMNetworkAdapter -VMName <name>` reports exactly one adapter — the single-adapter invariant `setup-guest.md` §1 already documents by convention ("Do not add a second adapter") but nothing today enforces. Both checks join the Step 0 pre-flight list below.

**Switch names are derived from the adapter-alias flags, not hardcoded separately.** The existing `--adapter-alias`/`--nat-adapter-alias` flags (default `vEthernet (susentorno-internal)` / `vEthernet (Default Switch)`) already identify the Hyper-V switches by their host-side adapter alias; Windows names that host adapter `vEthernet (<switch name>)` by construction, so the actual switch name passed to `Connect-VMNetworkAdapter -SwitchName` is derived by stripping the `vEthernet (` prefix and trailing `)` from each alias, rather than being hardcoded as separate `'Default Switch'`/`'susentorno-internal'` literals. This is a naming convention, not a guaranteed-durable identity — a management adapter could in principle be renamed independently of its switch — so Step 0's pre-flight checks (below) confirm both derived names resolve to real Hyper-V switches before any VM is touched, catching a bad derivation as a clear upfront error rather than a failure partway through `Connect-VMNetworkAdapter` after the VM has already been stopped.

## Guest address discovery across network transitions

Four distinct addresses are in play, and the rest of this design refers to them by these names to avoid confusion:

| Name | What it is | Resolved via |
| --- | --- | --- |
| Default-Switch **guest** IP | the guest's own DHCP lease on Default Switch | Hyper-V discovery or the prompted address (below) |
| Internal-switch **guest** IP | the guest's own DHCP lease on `susentorno-internal` | Hyper-V discovery only |
| Default-Switch **host** IP | the Windows host's own address on that network | `resolveForwardListenAddress`, unchanged from the original design |
| Internal-switch **host** IP | the Windows host's own address on that network | `resolveForwardListenAddress`, unchanged from the original design |

The two *guest* addresses are what every SSH call connects to; the two *host* addresses are what the SMB mount's source (`//<host-ip>/<share>`) points at. They're resolved completely independently — mount resolution doesn't change from the original design at all.

The prompted "Guest address" is only reliable for the phase it was typed in: the guest receives a **different** DHCP lease on the Default Switch than on `susentorno-internal`, so it's never valid after isolation, and it may not even survive a same-network reboot if the user typed a raw IP rather than a resolvable hostname. It is used for exactly one thing: the initial reachability check in step 1, racing it against Hyper-V-based discovery (below) rather than replacing it, since Hyper-V discovery cannot yet be trusted on a guest that has never run anything from this command before (next paragraph). Every address needed after that point — the rest of step 1 if a reboot happens, and all of step 5 — is discovered fresh via Hyper-V, never the prompt.

**Hyper-V-based discovery has a prerequisite this design must satisfy itself, not assume.** `(Get-VMNetworkAdapter -VMName <name>).IPAddresses` is populated by the guest's own Hyper-V Data Exchange (KVP) integration service reporting its address back to the host — a *different*, separate component from the `hv_vmbus`/`hv_utils` kernel drivers this design already relies on for graceful shutdown. Kernel driver support is built into Ubuntu's kernel and active by default; the userspace KVP daemon that actually reports the IP is a separate package, not installed on a stock Ubuntu Server image (confirmed by web search — see `hv_kvp_daemon`'s Ubuntu manpage and Microsoft's own Hyper-V troubleshooting doc for "`Get-VMNetworkAdapter` doesn't report IP addresses"). A freshly-created guest, per setup-guest.md's flow, has only `openssh-server` installed at the point this command first connects — Hyper-V discovery cannot be assumed to work yet.

The fix: this command ensures the KVP daemon package is installed as an explicit, guaranteed step — the same way `mountShare` already guarantees `cifs-utils` is installed rather than trusting it's already there — immediately after the first successful connection (using the raced prompted-address/Hyper-V-discovery check above), before mounting or running `pre-scripts/`. From that point on, for the rest of *this* run, Hyper-V discovery is reliable: it's what step 5 uses (no prompted address exists for the internal-switch network to fall back to), and what a *future* rerun's step 1 can rely on too, since the guest's disk already has the daemon installed from this run onward. (The exact package name — candidates seen include `hv-kvp-daemon-init` and `linux-cloud-tools-virtual` — should be confirmed against the specific Ubuntu LTS version setup-guest.md targets during implementation, not asserted here.)

Each reachability wait (step 1's initial check, and step 5's) polls for a candidate address and, once one appears, attempts a raw TCP connection to it (below) — this is where address discovery and reachability checking are the same loop, not two separate steps.

## Idempotent top-level flow

Every invocation runs the same fixed sequence — no phase-detection/resume logic, matching (and now extending across the whole command) the philosophy `runPreScripts` already established: a failed run is safe to retry from the top, because every built-in step is idempotent or convergent (see "Failure handling & idempotency limits" for the qualifications on that claim). `<default-switch-name>`/`<internal-switch-name>` below refer to the switch names derived from the `--nat-adapter-alias`/`--adapter-alias` flags (see "New input: VM name"), not literal strings — both are confirmed to exist as real Hyper-V switches during step 0, so a bad derivation is caught there rather than after a VM has already been stopped.

0. **Pre-flight checks**, all before touching the VM at all, though not all before the same point in the surrounding command: elevation (above) is checked first, before any prompting, since it needs no input. After the VM-name prompt: confirm the named VM exists uniquely (its resolved name matches the input exactly — `Get-VM -Name` supports wildcard patterns, so a resolved result is checked against the literal input rather than trusted as-is) and has exactly one network adapter; confirm both `<default-switch-name>` and `<internal-switch-name>` resolve to real Hyper-V switches. The `run-hosting` readiness check needs no prompted input (the Internal-switch host IP is auto-discovered, not asked for) and can run either alongside these or earlier: confirm `run-hosting`'s DHCP (UDP 67) and DNS (UDP 53) ports are actually bound on the Internal-switch host IP (`Get-NetUDPEndpoint` — confirmed to need no special permission and to return nothing when unbound). Fail fast with a clear message on whichever check fails first.
1. Query the VM's current state via `Get-VM`/`Get-VMNetworkAdapter` and reconcile to "running, attached to `<default-switch-name>`," rejecting any state other than `Off`/`Running` outright (a message telling the user the VM's current state and that it needs to be `Off` or `Running` first) rather than guessing how to handle `Saved`, `Paused`, or an in-progress transition:
   - `Running` + wrong switch: graceful `Stop-VM` (below) → `Connect-VMNetworkAdapter -SwitchName <default-switch-name>` → `Start-VM`.
   - `Off` + wrong switch: `Connect-VMNetworkAdapter -SwitchName <default-switch-name>` → `Start-VM` (no `Stop-VM` — it's already off).
   - `Off` + correct switch: `Start-VM`.
   - `Running` + correct switch: no power operation.

   If a `Start-VM` just happened, wait for reachability by racing the prompted Default-Switch guest address against Hyper-V-discovered candidates (above); if the VM was already `Running` + correct switch, the connection from a previous point in this same run is still valid and no new wait is needed. Once connected, ensure the KVP daemon package is installed (above) before proceeding.
2. Create-or-update the SMB mount to point at the resolved Default-Switch **host** IP (existing `mountShare`, with the active-mount fix below).
3. Run every `pre-scripts/` script in order (existing `runPreScripts`, unchanged, including the `configure-network` exact-remainder argument special case).
4. Re-check `run-hosting`'s DHCP/DNS ports (same check as step 0) — guards against `run-hosting` having been stopped sometime during the potentially multi-minute `pre-scripts/` run. Fail fast if not. Because mount and `pre-scripts/` have already run by this point, this check (unlike step 0's) cannot claim VM state is untouched — only that the isolating `Stop-VM` hasn't happened yet.
5. Isolate: graceful `Stop-VM` → `Connect-VMNetworkAdapter -SwitchName <internal-switch-name>` → `Start-VM`, then wait for reachability using Hyper-V-discovered candidates only (no prompted address exists for this network; the KVP daemon is already installed from step 1, so discovery is reliable here).
6. Create-or-update the SMB mount to point at the resolved Internal-switch **host** IP (same `mountShare`, called again with that IP — not the guest IP just discovered for SSH, a distinct address; see the table above).
7. Run every `post-scripts/` script in order (new `runPostScripts`, below).

A fresh guest (never isolated) still goes through step 1's full reconciliation logic — it's simply a fast no-op branch (`Running` + correct switch) when the guest is already in the expected state, per the table above, not a special case. A guest that's already been fully set up runs all 8 steps again unconditionally on a rerun — including a round-trip through Default Switch and back — trading a slower rerun for exactly one code path to reason about and test. That round-trip has a real consequence worth stating plainly, not just as "slower": an already-isolated guest is briefly reattached to the internet-facing Default Switch on every rerun, temporarily losing the isolation `susentorno-internal` exists to provide, for as long as steps 1–4 take.

## Isolation mechanics

**Hyper-V VM operations** (`Get-VM`, `Get-VMNetworkAdapter`, `Stop-VM`, `Connect-VMNetworkAdapter`, `Start-VM`) shell out to `powershell.exe` via `execa`, following the pattern `src/runHosting/abnormalExitAlert.ts` already established (`-NoProfile -NonInteractive -Command '<script>'`) — no new dependency. Unlike `abnormalExitAlert.ts`'s fire-and-forget detached call, these are awaited synchronously as a normal part of the command's control flow, so a failure surfaces directly rather than being silently swallowed. Argument/command-string construction is a pure function, unit-tested the same way `buildSshRunArgv`/`buildScpArgv` are today; the actual `execa` invocation is a thin wrapper exercised only by manual verification against a real Hyper-V guest, matching the precedent already set for `createSshRemoteExec`. This was smoke-tested directly against a scratch VM (`temp-vm`) during design: `Get-VMNetworkAdapter`, `Stop-VM`, `Connect-VMNetworkAdapter`, and `Start-VM` all behaved as expected once elevated, with the full stop/reconnect/start cycle completing in about a second on the Hyper-V side (that VM has no OS, so this measures only Hyper-V's own bookkeeping, not guest shutdown/boot time).

**Every value interpolated into a `-Command` string is PowerShell-quoted** — the VM name, both derived switch names, both adapter aliases, and any IP address passed to `Get-NetUDPEndpoint` — a distinct concern from the POSIX single-quoting `quoteForRemoteShell` already applies to values sent over SSH. A new `quoteForPowerShell` helper (doubling embedded `'` characters, PowerShell's own escaping rule for single-quoted strings) is applied at every one of those interpolation points, mirroring `quoteForRemoteShell`'s existing role for the SSH side; its unit tests cover values containing `'` and other PowerShell-significant characters the same way `quoteForRemoteShell`'s do for the shell side.

**`Stop-VM` is graceful, and does not fall back to a forced power-off automatically.** A plain `Stop-VM` requests an ACPI shutdown via the guest's Hyper-V integration services (present by default on modern Ubuntu kernels via `hv_vmbus`/`hv_utils`), letting the filesystem/journal shut down cleanly — and is only invoked when the VM is currently `Running` (per the reconciliation table above; an already-`Off` VM is left alone rather than assuming `Stop-VM` is a safe no-op against it). The 60-second graceful-shutdown bound is enforced at the process level — the `execa` call running `Stop-VM` is given a 60-second timeout and killed if it's exceeded — rather than relying on an assumption about whether `Stop-VM` itself blocks synchronously until the guest is off; either way (the call returns early or is killed at the deadline), the command then polls `Get-VM` to confirm the VM actually reached `Off`. If it hasn't, the command **fails** with a message describing the VM's current state and telling the user to investigate or force-stop it manually before rerunning — it does not call `Stop-VM -Force` on the user's behalf. A stuck graceful shutdown usually means something is genuinely wrong inside the guest (a hung process, stuck disk I/O); auto-forcing a power-off in that situation risks compounding whatever's already wrong, and this design already treats every rerun as a full power-cycle, so an unattended hard-off happening automatically on every problematic rerun is a real data-loss risk worth avoiding rather than a convenience worth keeping.

**The `run-hosting` readiness check** (steps 0 and 4) queries `Get-NetUDPEndpoint -LocalAddress <internal-switch-host-ip> -LocalPort 67` and `-LocalPort 53`; both must return a bound endpoint. This is a liveness precheck, not a full readiness guarantee — it confirms *something* is bound to the expected address and port right now, not that it's specifically `run-hosting`, that DHCP replies actually traverse the firewall, or that the process will still be up moments later. It exists to catch the single specific, expensive failure mode this design is built around (booting the guest into isolation with nothing there to answer DHCP), not to replace the troubleshooting steps `setup-guest.md` already documents for firewall-related failures. If either port is missing, the command exits with a message telling the user to start `run-hosting` and retry; at step 0 this happens before any VM state has been touched, at step 4 it happens after mount and `pre-scripts/` have already run (see step 4 above).

**Waiting for reachability** after a `Start-VM` (steps 1 and 5) is a TCP-level check, not an SSH connection: poll for a candidate guest IP — Hyper-V-reported, raced against the prompted address too in step 1 specifically (above) — and, once one appears, attempt a raw TCP connection to port 22 on it — a plain socket connect/close, not a full SSH handshake or authentication attempt. This deliberately avoids running real SSH commands during the wait: this command's SSH invocations are interactive by design (inherited stdio, so the guest's own login/host-key/sudo prompts reach the user directly), and a polling loop that shelled out to `ssh` every 10 seconds for up to 10 minutes would either hang on a password prompt per attempt or need its own separate non-interactive auth mode to avoid one. A raw TCP check needs neither, cleanly separates "is the network/SSH daemon up" from "can we authenticate" (the latter happens once, interactively, when the real mount/script commands start), and is trivially unit-testable against a fake clock and an injected connector with no subprocess involved. Each attempt is bounded by its own short connect timeout (5 seconds) so a single hung attempt cannot itself exceed the overall 10-minute deadline; polling repeats every 10 seconds for both the reassign-to-Default-Switch and isolate-to-Internal-switch directions alike. `setup-guest.md`'s documented ~5-minute worst case was observed when a *running* guest's adapter was changed live; this design always powers the guest fully off and back on for both transitions, so the guest's network stack performs a fresh DHCP negotiation at boot rather than depending on Linux's slower failed-attempt retry backoff — and with `run-hosting` now confirmed listening before the Internal-switch `Start-VM`, leases are expected to bind in under a second, per the existing doc's own measurement of that case. The 10-minute timeout is a generous backstop, not the expected common case. Progress reports through the existing `onStep` mechanism (e.g. "waiting for guest to become reachable... (40s elapsed)") so the wait is visible rather than a silent hang; a timeout error points at `setup-guest.md`'s troubleshooting section (the host-firewall "allow node.exe on public networks?" dialog, etc.).

## Mount step (reused, with one fix)

The existing `mountShare` create-or-update `/etc/fstab` handling (delete-then-append keyed on mount point, already convergent whether the mapping is missing, correct, or stale) is called twice — once with the Default-Switch host IP (step 2), once with the Internal-switch host IP (step 6). Same function, same idempotency guarantee already documented for `/etc/fstab` itself, just invoked at two points in the flow with different IPs.

One fix to the step's *last* command, `sudo systemctl daemon-reload && sudo mount -a`: `mount -a` only mounts entries from `/etc/fstab` that aren't already active — it does not detect or re-mount an entry whose *source* changed while the mount point is still (stale-)mounted. Step 6 is exactly that case: if the mount survived the isolation reboot in some active-but-stale state, or a prior run left it mounted against the old IP, rewriting `/etc/fstab` and calling `mount -a` again would leave the live mount pointed at the old, now-unreachable source, even though the file on disk is now correct.

The fix distinguishes "not mounted" from "mounted but failed to unmount," rather than swallowing both the same way: `mountpoint -q /mnt/<share-name> && sudo umount /mnt/<share-name>; sudo systemctl daemon-reload && sudo mount -a` is *not* used, because the `;` between `umount` and the rest would let a real unmount failure (a busy or hung CIFS mount) pass silently into `mount -a`, which would then skip the still-active stale mount and report success — recreating exactly the bug being fixed, just one layer deeper. Instead: check `mountpoint -q /mnt/<share-name>` first; if mounted, `umount` must succeed before proceeding — its exit code is checked the same way every other step in this design stops on a non-zero exit, not discarded — and only then does `daemon-reload && mount -a` run. If it isn't currently mounted, skip straight to `daemon-reload && mount -a`. A stuck/busy unmount that never returns is an accepted, undocumented-further risk here, the same category of risk as any other remote command that could hang (e.g. a stuck `apt-get` in a pre-script) — not something this design adds a new timeout mechanism for.

## Post-scripts execution

New `runPostScripts`, structurally identical to `runPreScripts` minus the `configure-network` argument special case — none of `post-scripts/`'s built-ins (`01-auth-config.sh`, `02-apply-home-jq-transforms.sh`) take arguments, and nothing in `setup-guest.md` documents one that does. `listPreScripts` becomes a directory-agnostic `listScripts(dir)` that both `runPreScripts` and `runPostScripts` call, rather than duplicating the numeric-prefix-ordering logic. Same `RemoteExec` seam, same stop-at-first-non-zero-exit semantics. `.susentorno/post-scripts/` already supports the same custom-script weaving mechanism as `.susentorno/pre-scripts/` (README's "Customizing setup scripts"), so a woven-in custom post-script runs in its resolved position automatically, with the same no-argument limitation and idempotency caveat already documented for custom pre-scripts.

## Console output for step announcements

Today, the shared `onStep` callback in `setup-guest-unix.ts` prints `setup-guest-unix: ${message}...` for every step, with no separation from whatever streamed output follows it on the same terminal — most visibly for `runPreScripts`' `running ${filename}` announcements (apt/pnpm/etc. logs can be long), but the same shared callback also announces each `mountShare` step immediately before that step's own SSH command runs. Every `onStep` call that precedes an SSH invocation — `mountShare`'s per-step messages, `runPreScripts`'/`runPostScripts`' per-script messages alike — gains a leading and trailing blank line; the existing `setup-guest-unix: ` prefix is unchanged, so the one shared `onStep` implementation formats consistently everywhere it's used:

```

setup-guest-unix: running 01-apt-packages.sh...

<script's own streamed output>
```

This does not extend to the Hyper-V/PowerShell-side operations (VM state queries, `Stop-VM`/`Connect-VMNetworkAdapter`/`Start-VM`, the `run-hosting` readiness check) — those aren't SSH calls, and keep whatever simpler status reporting the isolation-mechanics section above already describes.

## Failure handling & idempotency limits

Every step keeps today's "stop at first non-zero exit, print what failed, exit non-zero" behavior, now spanning the full pipeline. "Idempotent" is loosely used above the way `runPreScripts` already uses it, but is worth being precise about here: the pipeline is **restartable and convergent** — a rerun deliberately repeats shutdowns, switch changes, mounts, and script executions rather than resuming from where a previous run stopped — not idempotent in the strict sense of "running it twice has no additional effect." That's a sound recovery model given the individual steps really do converge (an already-correct `/etc/fstab` line, an already-`Off` VM start cleanly), but it rests on some things this spec doesn't fully verify:

- "Every built-in pre/post-script is idempotent in practice" is carried over from the original design's claim about `pre-scripts/`, extended here to `post-scripts/` without a fresh audit — auditing every built-in script (`01-auth-config.sh` especially, since anything that rotates or regenerates credentials on each run could break the "safe to rerun" guarantee) is an acceptance criterion for this work, not an optional follow-up, since the whole "rerun from the top is safe" recovery model depends on it actually being true.
- That guarantee is explicitly **not** extended to a woven-in custom script — same pre-existing user responsibility the README already documents for the customization mechanism, restated here rather than silently contradicted by the general "safe to rerun" framing above.
- A VM left `Off` or mid-switch-change after a failure between `Stop-VM`, `Connect-VMNetworkAdapter`, and `Start-VM` is recovered by step 1's reconciliation on the next run (above) — that reconciliation is what makes "rerun from the top" actually safe here, not an incidental side effect.

## Testing

Unit tests cover:

- Hyper-V/`Get-NetUDPEndpoint`/`quoteForPowerShell` command construction, including values containing `'` and other PowerShell-significant characters.
- `runPostScripts` orchestration (via the generalized `listScripts`).
- The address-discovery-plus-TCP-reachability poll against a fake clock and an injected connector: immediate success, timeout, an address that appears after several empty polls, an unresponsive port, and (for step 1 specifically) the prompted address and a Hyper-V-discovered address racing, either one winning.
- Step 1's full reconciliation table against injected `Get-VM`/`Get-VMNetworkAdapter` results: `Running`+correct switch (no-op), `Running`+wrong switch, `Off`+wrong switch, `Off`+correct switch, and every other state (`Saved`, `Paused`, a transitional state) failing with a clear message rather than guessing.
- VM/adapter validation: nonexistent VM name, a name that only matches via wildcard expansion (rejected), zero adapters, multiple adapters, a derived switch name that doesn't resolve to a real switch.
- The mount step's unmount logic: not-currently-mounted (skips straight to `mount -a`), successfully unmounted, and a failing `umount` correctly blocking `mount -a` from running at all (a regression test for the exact bug the fix addresses).
- The `Stop-VM` timeout: the `execa` call exceeding its 60-second bound, and the subsequent `Get-VM` poll confirming (or failing to confirm) `Off`.

`tests/guest/`'s QEMU harness cannot exercise anything Hyper-V-specific — VM stop/reassign/start, state reconciliation, the elevation check, or the `run-hosting` readiness check — since it doesn't run under Hyper-V at all; that entire isolation phase joins the existing SMB mount step as a documented manual-verification gap (same spirit as ADR-0010's existing fidelity-gap callouts for this harness). Given how much stateful, host-specific behavior this adds, that manual verification is a checked-in checklist (a concrete deliverable of this work, not a follow-up), covering at least: fresh guest end-to-end (confirming the KVP daemon package installs correctly and discovery starts working from that point on), full rerun of an already-completed guest, `run-hosting` not running at either readiness check, a graceful-shutdown timeout, a VM left `Off` on the wrong switch from an interrupted prior run, and confirming the final adapter/mount source/`post-scripts/` results are correct in both directions. `runPostScripts`'s own orchestration logic, independent of the isolation gap around it, can be exercised through the harness the same way `runPreScripts` is today.

## Documentation

`setup-guest.md`'s Ubuntu path collapses to: install `openssh-server`, run `susentorno setup-guest-unix`, done — the separate "Isolate" and "run `post-scripts/`" instructions for Ubuntu are removed from the main flow (Windows' existing manual flow is unchanged). The manual fallback callout grows to cover isolation and post-scripts as well, for diagnosing a failure or understanding exactly what the command does — and, while it's being rewritten anyway, fixes a pre-existing wart in today's version: the fallback's sample `/etc/fstab` line hardcodes `192.168.67.1` (the doc's running example host IP) immediately above prose that correctly says to use the Default-Switch host IP during the NAT phase instead, an inconsistency worth resolving rather than carrying forward.

New callouts, beyond the elevation prerequisite already noted above: `run-hosting` must already be running (and stay running) before the command isolates the guest; every rerun of an already-isolated guest briefly reattaches it to the Default Switch, temporarily losing isolation; a graceful-shutdown timeout fails rather than forcing power-off, and what to do about it; that a custom `pre-scripts/`/`post-scripts/` addition must be safe to rerun, since every invocation reruns the whole pipeline unconditionally; that the command installs a Hyper-V KVP/Data Exchange daemon package on the guest as part of its own setup (so guest address discovery works), separate from anything `pre-scripts/` itself installs; and a short explanation of the four distinct addresses in play (Default-Switch/Internal-switch, each split into guest and host) so a reader diagnosing a failure isn't left guessing which one a given error message refers to.

## Out of scope

- Windows Guest automation — unchanged from the original design.
- Depending on cross-adapter host reachability for the pre-isolation mount (see "Why the mount isn't just pointed at the isolated IP from the start") — the Default-Switch-host-IP approach remains the guaranteed-correct one.
- A persisted Guest/VM registry — the VM name, like every other prompt, is asked fresh each run, consistent with the original design's existing choice not to introduce a config file.
