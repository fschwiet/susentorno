# 02: Make a stalled golden build cheaper to diagnose

**Status:** ready-for-review

**Blocked by:** None (can start immediately).

## Problem

When the guest tier's golden Ubuntu build goes wrong, `waitForOff` (`tests/guest/hyperv/goldenImage.ts`) waits the full 45 minutes and then throws `build VM did not power off`, with only the serial log to go on. The [hand-off this came from](../handoff.md) shows what that costs:

- Two runs on 2026-10-26 spent about 90 minutes reaching the same uninformative error.
- `ensureGoldenImage` deletes `golden-build-serial.log` at the start of every build (`rmSync(goldenBuildSerialLogPath, ...)`), so the second failure destroyed the first one's log.
- The [earlier kernel-oops ticket](../../golden-image-installer-kernel-oops/issues/01-installer-kernel-oops-hangs-golden-build.md) had a kernel `Oops`/`BUG:` in the serial log about 40 minutes in, and the harness still waited out the deadline.
- The serial log could not tell "installer hung" from "serial reader lost the pipe". That question was only settled by looking at the VM's console and its network traffic from the host.

## Constraint learned from the diagnosis: serial silence is not a stall

The obvious design, "fail when the serial log hasn't grown for N minutes", fails healthy builds. In a build that went on to succeed (with `apt: { geoip: false }`), the serial log printed `start: subiquity/Mirror/cmd-apt-config` during `Install/install/configure_apt` and then **nothing for over 10 minutes**, while curtin installed packages and ran `unattended-upgrades` inside `/target`. The VM then powered itself off after about 26 minutes. A 4-minute and a 10-minute silence threshold both declared that build stalled.

Signals that did separate a real stall from a quiet healthy install in that session:

- **Network activity of the build VM**, seen on the host: the real stall sent no packets at all. Hyper-V's per-VM network metering, or adapter byte counters, may give this without a packet capture.
- **CPU**: about 0% in the real stall, against 4–16% while installing. CPU is a noisy signal on its own.
- **The live installer's state**: process list and `/var/log/installer/subiquity-server-debug.log`, readable through a tty2 shell. See the notes in [issues/01](01-pin-primary-mirror.md).

## Candidate pieces (to settle in design, not all required)

1. **Keep the previous run's serial log**, for example by rotating it to `golden-build-serial.prev.log` rather than deleting it. This is cheap and independent of the rest.
2. **Fail fast on an unambiguous kernel failure**: a serial line matching `Oops`, `BUG:`, `general protection fault` or `Kernel panic`. That has no false-positive risk from quiet phases.
3. **Capture evidence when the build fails** (at the deadline, or at an early-failure trigger): `Get-VM` state, uptime, CPU and memory; a 640x480 console screenshot (`tests/guest/hyperv/vmScreenshot.ts` uses 320x240, which is unreadable); and, if practical, the tail of `subiquity-server-debug.log` from the live VM.
4. **An early stall trigger that tolerates quiet phases**, if one is worth having. Options include combining serial silence with no network traffic and near-zero CPU over a window, or applying a silence threshold only before Subiquity's `Install` step begins. Weigh the false-red risk against minutes saved: a false red on a healthy build costs a full rebuild.

## Questions for design

- Is piece 4 worth its false-red risk, or do pieces 1–3 deliver most of the value?
- Should failure evidence go next to the serial log in `.image-cache/`, which survives across runs, or into the run's `test-results/` directory?
- Does the Windows golden build (`windowsGoldenImage.ts`) want the same treatment? It already captures screenshots.

## Comments

### 2026-11-01: Triage — ready-for-agent

> *This was generated by AI during triage.*

Decisions from triage with the maintainer:

- **Piece 4 (early stall trigger) is out of scope.** Pieces 1–3 cover both failures seen so far (the kernel oops and the geoip stall). A traffic/CPU-based trigger has no measured thresholds, and a false red costs a full rebuild. Reopen as a separate ticket if stalls without a clear signal recur.
- **Build evidence moves out of `.image-cache/`.** `.image-cache/` is for reusable cached images and their inputs. Evidence describes a build *attempt*, and nothing about it needs to sit beside an image: a failed attempt leaves no usable image, and the stamp file already ties an image to its inputs. The only stated reason for putting evidence in `.image-cache/` was to survive into the next run, and `test-results/` already does that: only per-run subdirectories are created under it, nothing deletes it wholesale, and it is gitignored. This applies to both the new failure evidence and the existing evidence (the Ubuntu serial log and the Windows build screenshots).
- **The Windows golden build keeps its behaviour.** Only its screenshot directory moves.

## Agent Brief

**Category:** enhancement
**Summary:** Make a failed golden Ubuntu build cheap to diagnose. Keep the previous attempt's evidence, fail fast on a kernel failure in the serial log, capture VM state and a legible console frame on failure, and move all golden-build evidence from `.image-cache/` to `test-results/golden-build/`.

**Current behavior:**

- `ensureGoldenImage` deletes the serial log (`goldenBuildSerialLogPath`, `.image-cache/golden-build-serial.log`) at the start of every build, so a second failure destroys the first one's evidence.
- `waitForOff` polls `Get-VM` every 15 s for up to 45 minutes. It ignores the serial log's contents, so a kernel oops printed early still costs the full 45 minutes. It then throws `build VM did not power off; see <serial log>`, with no other evidence.
- The `finally` block stops the serial reader and removes the build VM. By the time anyone looks, the VM's state and console are gone.
- Console frames come from `buildThumbnailCommand` / `captureScreenshotFrame`, which are fixed at `SCREENSHOT_WIDTH` × `SCREENSHOT_HEIGHT` (320x240). Text is unreadable at that size; 640x480 is legible.
- The Windows golden build writes its periodic screenshots to `windowsBuildScreenshotDir` (`.image-cache/windows-build-screenshots`). Comments next to both paths say they are "deliberately not under test-results/<timestamp>/".

**Desired behavior:**

1. **Evidence location.** All golden-build evidence lives under `test-results/golden-build/`, outside `.image-cache/`:
   ```
   test-results/golden-build/
     ubuntu/
       current/     serial log + failure evidence for the latest attempt
       previous/    the attempt before it
     windows/
       screenshots/ the Windows build's periodic frames (behaviour unchanged)
   ```
   `.image-cache/` holds only cached images, their stamps, the ISO, and harness keys/credentials. Existing evidence files left in `.image-cache/` from earlier runs are not migrated or deleted by code.
2. **Attempt rotation (Ubuntu).** When a golden Ubuntu build actually starts (not when the stamp matches and the cached image is reused), the old `previous/` is removed, `current/` (if present) is moved to `previous/`, and a fresh `current/` is used for this attempt. The serial log and any failure evidence rotate together.
3. **Fail fast on a kernel failure.** While waiting for the build VM to power off, the harness also checks the serial log for an unambiguous kernel failure: lines containing `Oops`, `BUG:`, `general protection fault`, or `Kernel panic`. On a match it stops waiting and fails the build at once, without waiting for the deadline. The error message names the matched line and the evidence directory. Real lines from the earlier kernel-oops ticket that must match:
   ```
   [ 2458.169321] BUG: unable to handle page fault for address: ffffffffc0815f50
   [ 2458.180263] Oops: Oops: 0000 [#1] SMP NOPTI
   [ 2474.490586] Oops: general protection fault, probably for non-canonical address 0xccccccccccccccfd: 0000 [#2] SMP NOPTI
   ```
   Ordinary healthy-install serial output (Subiquity `start:`/`finish:` events, cloud-init, systemd) must not match.
4. **Failure evidence capture.** When the build fails, whether at the 45-minute deadline or on a kernel-failure match, the harness writes into `current/` **before** the VM is turned off and removed:
   - VM state as text: at least `State`, `Uptime`, `CPUUsage`, `MemoryAssigned`, `MemoryDemand`, and `Heartbeat` from `Get-VM`;
   - one console frame at 640x480 as a BMP.

   Capture is best effort. A failure while capturing evidence must neither replace the original build error nor prevent the build VM from being cleaned up. The thrown error points at the evidence directory.
5. **Thumbnail size becomes a parameter.** Frame capture accepts a width and height instead of always using 320x240. Existing callers (the Windows build's periodic capture and the Windows role diagnostics) keep 320x240 unless they opt in.
6. **Windows path move only.** `windowsBuildScreenshotDir` points at `test-results/golden-build/windows/screenshots/`. How the Windows build captures, retains, and clears frames is unchanged.
7. **Docs and comments follow.** Update the comments on the evidence path constants: they no longer argue for `.image-cache/`, and should say why evidence lives under `test-results/golden-build/` rather than in a per-run `test-results/guest/<timestamp>/` directory. Update `testing.md`'s guest-tier diagnostics description to mention where golden-build evidence lands.

**Key interfaces:**

- `goldenBuildSerialLogPath` (image-cache module): replace it with an Ubuntu golden-build evidence directory, `current`/`previous`, from which the serial log path derives. Whether that is a constant pair or a small helper is the agent's choice.
- `windowsBuildScreenshotDir`: new location, same role.
- `ensureGoldenImage(exec, keys, opts)`: signature unchanged. Rotation happens only on the rebuild path.
- `waitForOff` (Ubuntu golden build): gains the serial-log kernel-failure check alongside its `Get-VM` polling. The 45-minute deadline and 15 s poll interval stay.
- A pure matcher for kernel-failure lines (string in → matched line or nothing), so it can be unit-tested without Hyper-V.
- `buildThumbnailCommand(vmName, width, height)` already takes a size. `captureScreenshotFrame` and the RGB565 payload trim inside it need to honour a caller-supplied size instead of the `SCREENSHOT_*` constants.
- `isSweepableChildVhd`'s unit test lists `golden-build-serial.log` as a non-sweepable `.image-cache/` entry. Drop or adjust that entry once the log no longer lives there.

**Acceptance criteria:**

- [ ] Unit tests cover the kernel-failure matcher: the three sample lines above match, and representative healthy serial lines (e.g. `start: subiquity/Mirror/cmd-apt-config: curtin command apt-config`, `finish: subiquity/Install/install/configure_apt: ...`, cloud-init and systemd status lines) do not.
- [ ] Unit tests cover attempt rotation against a temp directory: first attempt (no `current/`), second attempt (`current/` → `previous/`), third attempt (old `previous/` replaced). Nothing from an older attempt survives in `current/`.
- [ ] Unit tests cover the `Get-VM` evidence command builder (including quoting of the VM name), and a 640x480 frame capture producing a BMP whose header reports 640x480. The second can use a fake `PowerShellExec` returning a synthetic payload, as the existing screenshot tests do.
- [ ] Existing screenshot tests still pass, and Windows callers still capture at 320x240.
- [ ] No production or test code writes golden-build evidence (serial log, failure evidence, Windows build screenshots) under `.image-cache/`. `grep` for the old path names finds no live references.
- [ ] `pnpm check` stages up to and including `unit` pass (format, lint, typecheck, unit). Read `testing.md` for tier placement; new tests here belong in `unit`.
- [ ] If a guest-tier run is feasible (elevated shell, Hyper-V; see `testing.md`), a forced Ubuntu golden build still completes and leaves its serial log in `test-results/golden-build/ubuntu/current/`. If it is not feasible, say so in the hand-off rather than claiming it was verified.

**Out of scope:**

- Any early stall trigger based on serial silence, network traffic, or CPU (piece 4 of the original ticket).
- Reading the live installer's `subiquity-server-debug.log` via tty2 keystrokes as part of failure evidence.
- Changing the Windows golden build's behaviour (capture cadence, retention, rotation, fail-fast) beyond its screenshot directory moving.
- Changing the 45-minute deadline, the autoinstall config, or the golden stamp inputs. Evidence location is not a stamp input; no `BUILD_ALGORITHM_VERSION` bump.
- Migrating or deleting old evidence files already in `.image-cache/`.
